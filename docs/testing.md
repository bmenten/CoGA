# Test Overview

A catalogue of CoGA's automated tests: **what each test file verifies**, with a link to the
file. This is the file-centric view. For the requirement-centric view (each requirement and
its verifying test), see the Requirements Traceability Matrix,
[TF-09b](regulatory/TF-09b-requirements-traceability-matrix.md).

Backend tests run with `pytest` (Python), frontend tests with `vitest` (TypeScript/React).
The test tree is the source of truth for the counts; the commands under
[Keeping this current](#keeping-this-current) print them.

---

## Test strategy

- **Unit-first, self-contained.** The backend unit suite mocks Postgres and ClickHouse and
  needs no service containers. Pure analysis logic (NIPT, haplotype/PGT, ACMG/CNV, mtDNA,
  prioritisation) is tested directly on synthetic inputs.
- **Integration and end-to-end.** Integration tests boot the real app against Postgres and
  ClickHouse (schema, admin seed, health probe) to catch startup and schema failures the unit
  suite cannot. The end-to-end harness runs the golden-trio pipeline and the demo bundles
  against documented expected results.
- **Frontend components and logic.** `vitest` and Testing Library cover the pure `lib/`
  logic, the visualization components (canvas mocked) and page behaviour. Safety-relevant UI
  (route guards, ACMG/CNV/NIPT readouts, sign-out and drift) is covered explicitly.
- **Fail-safe on degraded input.** In NIPT, ACMG, CNV and haplotypes, degraded or empty input
  must abstain (low confidence, VUS, uninformative), never silently mis-call.
- **One backend test root.** Every backend test lives under `backend/tests/`, the only
  `testpaths` entry in `pyproject.toml`, so `pytest` collects the same suite from the
  repository root and from `backend/`. `scripts/check-test-catalogue.sh` fails on a test file
  outside it.

## How to run

```bash
# Backend: the unit suite (mocked datastores)
python -m pytest -q

# Backend: integration and end-to-end tests (need Postgres and ClickHouse running)
RUN_INTEGRATION=1 python -m pytest backend/tests/integration -q
RUN_INTEGRATION=1 python -m pytest backend/tests/e2e -q

# Frontend: the full gate, as in CI
cd frontend && npm run tsc && npm run lint && npm run test
```

Without `RUN_INTEGRATION=1` the integration and end-to-end tests are skipped. The
repository's `conftest.py` points Postgres and ClickHouse at a closed loopback port, so a unit
test reaches no database, a running dev stack's included (ENG-16). The CI jobs' datastore
settings are in `.github/workflows/ci.yml`.

## Continuous integration

`.github/workflows/ci.yml` runs these jobs on every pull request, every push to `main` and
every merge-queue group (`merge_group`). The security gates (`deps`, `secret-scan`, `codeql`)
are in `.github/workflows/security.yml`, which runs on the same events. The three jobs that
start the app against the datastores (`smoke`, `e2e`, `e2e-playwright`) share one block of
datastore settings.

| Job | What it runs | Notes |
| --- | --- | --- |
| **backend** | `pip install -r backend/requirements-dev.txt`, `ruff check .`, `mypy`, `scripts/generate-api-types.py --check`, `pytest -q` | Lint (`[tool.ruff]` in `pyproject.toml`); a type check of the clinical-critical modules under `[tool.mypy]`; a check that the frontend's generated API types (`frontend/src/lib/apiSchema.generated.ts`) match the backend's OpenAPI schema; then the unit suite with its coverage floors, which fail if a module the type check lists has none. The whole backend's floor is 74 %, in pytest's `--cov-fail-under` and in `scripts/check-coverage-floor.py`; pytest rounds the total to whole percent first, the script does not. |
| **smoke** | `pytest backend/tests/integration` against Postgres and ClickHouse service containers | The real startup: schema migration (baselines and revisions), admin seed, health probe. Records coverage for the `coverage` job. |
| **e2e** | `pytest backend/tests/e2e` against the same services | The golden-trio pipeline and the demo bundles against documented expected results (see [TF-09c](regulatory/TF-09c-e2e-pipeline-verification.md)). Records coverage for the `coverage` job. |
| **coverage** | combines the `backend`, `smoke` and `e2e` coverage data, then `scripts/check-coverage-floor.py --combined` | Floors on the combined figure for the modules only real datastores exercise (import pipeline, integrity anchors, sign-out), which the unit job under-reports. It installs coverage.py alone, with the pin and hashes of `backend/requirements-dev.txt`; the floor script needs only the standard library. A required check. |
| **frontend** | `npm ci`, `npm run tsc`, `npm run lint`, `npm run test:coverage` | Type check, ESLint and vitest. The type check includes `src/lib/apiContract.ts`: each hand-written API type in `apiTypes.ts` must accept the response shape the backend's schema declares. A response with a generated type is read through it (ENG-7). The React hooks and jsx-a11y rules are errors; `npm run lint` fails on any warning (`--max-warnings 0`). vitest fails below the coverage floors in `vite.config.mts`: a global one and one for `components/visualizations`. |
| **e2e-playwright** | seeds the golden trio, then Playwright drives Chromium against a uvicorn backend and the production frontend (the built bundle served by `server.mjs`, with its CSP) | Browser journeys; see [TF-09d](regulatory/TF-09d-browser-e2e-verification.md), which includes a manual procedure for auditors. |
| **sbom** | CycloneDX SBOMs for the backend and the frontend, uploaded as artifacts | Supply-chain evidence (see [sbom/README.md](../sbom/README.md)). Not a required check. |
| **lock** | `scripts/compile-requirements.sh` (pip-tools 7.4.1 with click 8.1.8 on Python 3.12, in Docker, for linux/amd64), then `git diff` of `backend/requirements.txt` and `backend/requirements-dev.txt` | Fails when a lock differs from what the script compiles from the `.in` files: a pin the `.in` files no longer allow, a package missing or left over, a `# via` line, the Python it names or the header's command line (TF-13 S-7). pip-compile keeps each pin that still fits and reuses its listed hashes, so the job checks no hash against PyPI; pip does, for each file it installs. The header's `pip-compile` command line is compared too: click renders it, and the script pins click, so it writes the same line on every run. Needs Docker Hub and PyPI. Not a required check. |
| **images** | `docker build` of `backend/Dockerfile` and `frontend/Dockerfile` at their `production` targets, as `ci/cloudbuild.*.yaml` build them: the repository root as context, the same build arguments, the backend stamped with the version `scripts/build-version.sh` prints (`VERSION` as a development build) and the 12-character commit, as `build.yml` stamps a build of `main`. Then each image runs one command: the backend imports the app and reports that version and commit, the frontend loads `server.mjs` and holds `dist/index.html`; neither runs as root | `build.yml` builds the images only after a merge, and not until Google Cloud is configured, so this build checks a pull request's Dockerfiles. Nothing is pushed: the job has no registry credentials. `backend/tests/test_deployment_config.py` fails when these builds drift from Cloud Build's. Not a required check: making it one is the owner's setting in branch protection. |
| **catalogue** | `scripts/check-test-catalogue.sh`, then `scripts/check-handleiding-sync.sh` | Fails when a test file has no row here or a row names a file that no longer exists, and when the handleiding HTML no longer matches its Markdown chapters. |

Twelve checks are required status checks on `main` (the ruleset `CoGA_branch_protect`):
`backend`, `frontend`, `coverage`, `smoke`, `e2e`, `e2e-playwright` and `catalogue` from
`ci.yml`, `deps`, `secret-scan` and the two `codeql` checks (Python, JavaScript/TypeScript)
from `security.yml`, and GitHub's `CodeQL` code-scanning result. A branch need not be up to
date with `main` before it merges. `sbom`, `images` and `lock` run but are not required.
Every job of the two workflows also runs for a merge-queue group, as does `build.yml`'s
Terraform check (never its build, deploy or SBOM jobs), so the ruleset can require GitHub's
merge queue; it does not yet (OPS-22). How the protection is enforced, and where it falls
short, is in [TF-18 §6](regulatory/TF-18-change-configuration-management.md).

### Browser end-to-end (Playwright)

`frontend/e2e/*.spec.ts` drive a real Chromium against a running stack: a uvicorn backend and
the production frontend (the built bundle served by `server.mjs` with its enforcing CSP and
`/api` proxy). It is the only suite that exercises the actual UI. Every journey fails if the
browser reports a CSP violation (`e2e/fixtures.ts`). Run it locally with the datastores up:

```bash
python scripts/seed_playwright_e2e.py   # golden trio + a known e2e user
cd frontend && E2E_PYTHON=/path/to/python npx playwright test
```

`E2E_FRONTEND=dev` runs the journeys against the Vite dev server instead (faster, but no build
and no CSP). `E2E_BACKEND_PORT` moves the backend off port 8000 when it is taken.

| Spec | Journey |
| --- | --- |
| [frontend/e2e/auth.spec.ts](../frontend/e2e/auth.spec.ts) | Login form: bad credentials stay on /login; the seeded e2e user logs in and lands authenticated. |
| [frontend/e2e/family.spec.ts](../frontend/e2e/family.spec.ts) | Open the golden family workspace and render the genome overview tracks: frontend-backend wiring and visualisation render. |
| [frontend/e2e/findingReview.spec.ts](../frontend/e2e/findingReview.spec.ts) | Review a repeat locus of the golden trio from its card: the dialog offers the repeat scale and no ACMG class tag; the saved classification and note show on the card at once and after a reload, read from the server. |
| [frontend/e2e/security-headers.spec.ts](../frontend/e2e/security-headers.spec.ts) | The production frontend server sends its security headers: CSP (`default-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`), `X-Content-Type-Options` and `Permissions-Policy`. |
| [frontend/e2e/signout.spec.ts](../frontend/e2e/signout.spec.ts) | Clinical report sign-out from the browser: the live report of the seeded report-tagged variant renders; sign-out handles the drift and sample-QC override dialogs; the page then shows the signed version, rendered from its record, with its version advanced and the family's data still matching. |

### Stylesheet changes (computed-style diff)

A CSS change can be checked for what it renders, not only for what it says.
[frontend/scripts/stylediff](../frontend/scripts/stylediff/README.md) renders two production
builds against the same seeded stack (golden trio, NIPT demo, demo quartet) and compares every
element's computed style, pseudo-elements and box, over ~110 routes at three widths, with
forced `:hover`/`:focus`, expanded `<details>` and print media. It is a manual tool, not a CI
job. It verified the CSS clean-up of #712: no element rendered differently.

## Regulatory traceability

Tests are traced **from requirements** in
[TF-09b — Requirements Traceability Matrix](regulatory/TF-09b-requirements-traceability-matrix.md)
(each `REQ-…` → implementation → verifying test → hazard). The verification strategy is in
[TF-09 — V&V Plan](regulatory/TF-09-verification-validation.md). This document is the
complementary file→purpose index.

## Keeping this current

The catalogue is maintained by hand and a **CI guard enforces it**: the `catalogue` job runs
[`scripts/check-test-catalogue.sh`](../scripts/check-test-catalogue.sh). It fails if a test file
is missing from this document or this document names a test file that no longer exists. Run it
locally before pushing:

```bash
./scripts/check-test-catalogue.sh
```

To regenerate the file list and per-file test counts:

```bash
# backend
for f in $(git ls-files 'backend/tests/*.py' 'backend/tests/**/*.py' | grep -E 'test_.*\.py$' | sort); do
  printf '%s\t%s\n' "$(grep -cE '^\s*(async )?def test_' "$f")" "$f"; done
# frontend
for f in $(git ls-files 'frontend/src/**/*.test.ts' 'frontend/src/**/*.test.tsx' | sort); do
  printf '%s\t%s\n' "$(grep -cE '\b(it|test)\(' "$f")" "$f"; done
# suite totals (a parametrized test counts once per case)
python -m pytest -q --co | tail -1
(cd frontend && npx vitest run | grep -E 'Test Files|Tests ')
```

When you add a test file, add a row to the relevant section here. If it verifies a
technical-file requirement, also update [TF-09b](regulatory/TF-09b-requirements-traceability-matrix.md).
