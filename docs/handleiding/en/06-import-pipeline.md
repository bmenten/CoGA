# 6. Package import — manifest, checks and traceability

CoGA reads in a complete family package of genome data in one controlled operation. The package comes from a folder on disk, passes a *manifest* and a series of checks, and ends up in Postgres and ClickHouse. The common thread: an auditor must be able to trace afterwards *which file, made with which tools, ended up in which table*. The reference for administrators and developers is `docs/data-import.md` (folder layout, manifest format, settings); the provenance of versions is in `docs/annotation-provenance.md`.

A few terms:

- **Manifest:** a YAML or JSON file (`manifest.yaml`) that lists which datasets a family contains and where each file is, like a packing list.
- **PED:** the classic pedigree file (six columns) with the family members and their parents.
- **VCF:** the standard format for variants. The `##` lines at the top (the *header*) name the tools used and their versions.
- **Dry-run:** a trial run that checks everything but writes nothing.

## The pipeline at a glance

Only a superuser or an administrator can import: every endpoint of the router `/api/family-imports` requires `get_current_superuser` (chapter 2). Overwriting an existing family is for an administrator only, like every replacement and deletion of a family's data (REQ-SEC-002). `POST /api/family-imports/deliveries/{id}/approve` with `conflict_mode: "overwrite"` and without a dry run refuses anyone else with `403` and *Only an administrator can overwrite an existing family: import with update to add the missing datasets, or ask an administrator.* (`OVERWRITE_ADMIN_ONLY_DETAIL`). A superuser may run such an overwrite as a dry run, and may import with `cancel` and `update`.

| Endpoint | Purpose |
| --- | --- |
| `GET /family-imports/packages` | The family folders that can be added by hand, each with the families that were loaded from it |
| `GET /family-imports/deliveries` | The deliveries, with their state |
| `POST /family-imports/deliveries` | Add a folder to the deliveries by hand (a `project_id` without a project gets `404`) |
| `GET /family-imports/deliveries/{id}/package` and `POST …/revisions` | Read and correct the package of a delivery |
| `POST /family-imports/deliveries/{id}/approve` and `/refuse` | Approve a delivery (also as a dry run; the import is then queued) or refuse it |
| `POST /family-imports/deliveries/{id}/archive` | Confirm the vanished package folder of an imported delivery as deliberately archived, with a reason |
| `GET /family-imports` and `GET /family-imports/{job_id}` | Follow the status |

The import does not run in the web request but in a **background worker**, so that a large package does not block the server. The worker takes the next job, validates the package, registers the family and then imports dataset by dataset. Under Docker Compose the workers run in a process of their own, the service `import-worker`, not in the backend. That way every import gets its own processor core and does not hold up users' requests (chapter 4). A job stays `queued` as long as no worker is running.

**Where in the code:** `backend/app/routers/family_imports.py`; the orchestration and the worker in `backend/app/services/family_package_import.py`.

## Where the package comes from

A package reaches an import only as a delivery: delivered into an import watch folder, or added to the deliveries by hand (below). Both read only local folders under `FAMILY_IMPORT_ROOTS`; you mount a bucket as a local folder (on Google Cloud the folder `imports/` of the PHI bucket, read-only at `/data/imports`). A folder with a scheme (`gs://`, `s3://`) in that list stops the backend at start-up. CoGA writes nothing into a package folder, so a share or bucket that is mounted read-only works as it is.

**The manifest CoGA keeps.** Every import reads the manifest that CoGA keeps: the manifest that the package of an approved delivery makes (`coga_package_manifest.package_manifest`), with the members under `family.add_members`, never a file in the package folder.

- The job stores it in `family_import_jobs.manifest_text`, with its SHA-256 in `manifest_sha256`. A worker that picks up the job, including a worker that picks it up again after the job's worker stopped, reads the stored text.
- The paths are relative to the package folder and the same guards apply: a path out of the folder is refused. A manifest file in the folder, even a symbolic link, is just a file: no import opens it.
- The validation report names the manifest it read: `manifest_source` (`coga`) and `manifest_sha256`. The family's package record for the package's analysis (`families.metadata.package_imports`) keeps both. The family's files (`raw_import_files`) hold a managed copy of it, as dataset `manifest`, to download and verify.

**Loaded folders are marked.** A package folder stays on the share after the import: CoGA never moves it, and shows the alignments and the QC report from it. The list of folders that can be added by hand therefore gives, for each folder, the families one of whose package records names that folder as the folder they were loaded from (`folder_path` of a record in `families.metadata.package_imports`, with or without a trailing `/`); a family loaded for two analyses from two folders is listed under both. It also gives when their last import from that folder registered them, and whether that import is unfinished or still running (the family carries the flag *import incomplete*, or the marker of a running import). The form marks such a folder as *imported*: add it again only to add or replace data, with update or overwrite. The list reads the families' records, not the folders; a folder whose family was deleted is not marked. A folder whose last import was undone because the package changed while it was being read is flagged (`changed_during_import`). **Where in the code:** `backend/app/services/imported_package_folders.py`.

**A package that changes after it was checked.** A package folder is the output of a pipeline on a share that other machines also write to, and an import is validated, queued and run at different moments. To see that the folder changed in the meantime without reading the content of the files, CoGA takes a **fingerprint** of the package: a SHA-256 over every item of the folder, at every depth (for a file the path, the size and the modification time in nanoseconds; for a symbolic link the path and the target, without following the link), and over the manifest that CoGA keeps for the import, if there is one. Files that a file manager writes and that no import reads (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `._*`) do not count, and an empty folder adds nothing. **Where in the code:** `backend/app/services/family_package_fingerprint.py`.

- The check takes the fingerprint before it reads the folder, and reports it (`package_fingerprint`). A folder with more than 100,000 items (`package_folder_too_large`, probably an import folder chosen by mistake) or a folder that cannot be read (`package_folder_unreadable`) is refused before anything in it is read.
- A delivery keeps the fingerprint with which its check read the folder. If the folder's fingerprint differs when the delivery is approved, the approval gets `409` and no job is created.
- The job stores the fingerprint of the folder as it enters the queue (`family_import_jobs.package_fingerprint`).
- When the job starts, the check takes the fingerprint again. If it differs from the one taken at queueing, the job ends `failed` with `package_changed_since_queued`, and nothing has been written. The job log names the fingerprint with which the import read the folder.
- After every dataset, and once more after the last one, the import takes the fingerprint again. If it differs from that of the check, or the folder cannot be read any more, what the import read may be partly the old and partly the new package: the import stops and is **undone** (owner's decision, 2026-11-05). Every dataset it wrote or still had to do counts as failed; a dataset that an update skipped wrote nothing and stays skipped. A family that the import created is deleted with everything on it, including the managed copy of a stored manifest. For an existing family the datasets are restored from the snapshot taken before the datasets (with an update just as with an overwrite, as soon as the package has a fingerprint), and so is what the registration wrote (`put_back_family_package_record`): the package record of the package's analysis, the family's analyses, what it wrote of each sample (its assays, its capture panels, its manifest entry and its package records, as the record keeps them in `previous_samples`), and the rows of the raw files from the package folder when no record names that folder any more, with the copy of the manifest CoGA kept for the job. The records of its other analyses stay as they are. The pedigree that the registration changed stays, as with every failed overwrite; every change is on the clinical audit trail. If the restore fails, the family gets the flag *import incomplete*. The job ends `failed` with `package_changed_during_import`, and the list of folders offers the folder again, with the label *changed during import*. Import the package again when it is finished, first with a dry run.
- The package record of the package's analysis keeps the fingerprint with which it was loaded (`package_fingerprint` in `families.metadata.package_imports`).

**Import watch folders.** A pipeline, or the step that copies its output to the share, can deliver a package without anyone typing the path: it writes the package folder into its project's folder in an **import watch folder** (`<watch folder>/<project>/<package>`), with its **package file** `coga-package.json`. The watch folder holds one folder per project, with exactly the name of the project in CoGA (owner's decision of 2026-11-10). A delivery in the folder of a project other than the one its package file names needs attention (`package_project_folder_differs`), as does a package folder placed directly in the watch folder (`package_not_in_project_folder`): correct the project in *Deliveries*, or move the folder to its project's folder. That one file describes the package in place of a PED, a manifest and a ready marker, and its `status` says when the package is complete (`docs/coga-package.md`). The watcher finds the delivery, checks it once and stores its state. It imports nothing: on the page *Package import* a person approves every delivery that is ready. **Where in the code:** `backend/app/services/import_watcher.py`, `backend/app/services/coga_package.py` and `backend/app/services/coga_package_manifest.py`.

- **Settings.** `FAMILY_IMPORT_WATCH_ROOTS` names the watch folders: local folders under `FAMILY_IMPORT_ROOTS` (a folder outside the import folders is not watched; a mounted bucket is, through its folder). Empty, the default, means that no folder is watched; the rounds run all the same, for what they do beyond the watch folders (recording the end of an approved delivery's import, offering a failed one again, following the folders of imported deliveries), which a folder added by hand needs too. `FAMILY_IMPORT_WATCH_INTERVAL_SECONDS` (default 300) is the time between two rounds. The watcher runs where the import workers run: in every import worker process, and in the API if it runs imports itself. Only one watches at a time: it holds a Postgres advisory lock on a connection of its own.
- **The package file** (format `coga-package/1`): a JSON object of at most 20 MB, always written in full, first under a temporary name and then renamed. Every file contains `schema`, `status`, `written_at` and `pipeline` (`name`, `version`, `run_id`); a complete file (`status: complete`) also `project` (the unique project name), `assembly` (that of the project, compared on build: `GRCh38.p14` and `hg38` belong to a GRCh38 project), `analysis_type`, `family` (with `family_id`, and optionally `roi` and the PGT details) and `files`: per file the path in the folder, the size and a `sha256` or `md5`. `members` is the pedigree (the import reads no PED), `datasets` the dataset block of a manifest; if a file leaves them out, CoGA proposes them from the folder, as Discover does, and the delivery warns about it. The optional `reference` is the FASTA the pipeline aligned to: the import sets it as the reference assembly in the family's annotation manifest. A field the format does not know is refused. The full description is in `docs/coga-package.md`.
- **A run in progress.** If the package file says `running` or `failed`, the folder is not a delivery: the pipeline is still writing it, or stopped. An earlier open delivery of that folder becomes `superseded`, with the run noted, until the file says `complete` again.
- **A round.** In every watch folder, every package folder with a complete package file is one delivery per fingerprint: a folder that changes is a new delivery. A new delivery is checked once: the package file; the size of every file (otherwise `incomplete`: the copy is still running); the checksum of every file for which the package file gives one (a checksum is optional: without one CoGA computes the SHA-256 itself and the delivery warns that the copy was not checked against the pipeline's output, `package_files_without_checksum`; the import takes over that SHA-256 instead of reading every file again); the pipeline's QC, the project and its assembly; the manifest that CoGA makes from the package file and that the delivery keeps; a PED in the folder that says something other than the members (a warning: the pipeline's tools may have read it); the validation as a dry run does it; that every file the import reads is in the package file (a file that is not in it, such as a CRAM put into the folder later, CoGA adds to the package itself, with its size and the SHA-256 it reads, and the delivery warns, `package_files_proposed`: the approver checks it; the owner's decision, 2026-11-23); and a family or samples that already exist (an existing family calls for a choice of update or overwrite, never a new family). If anything fails, the delivery is `needs_attention`, with every error as a reason; otherwise `ready`. An open delivery (`ready` or `needs_attention`) that the watcher sees again is checked again as soon as what CoGA holds has changed since its check: the project the package file names (added, deleted or of a different assembly), or a family or samples of the package (loaded or deleted). If you add the missing project, the delivery is `ready` at the next round, without the folder changing. What the check read of the family (the members' values, their links, the region, the package records) it also keeps as a digest (`family_state`): if you change a member in the members editor, or the region on the family page, as a reason asks, a new check follows. It stays the same delivery; the event `import_delivery_checked_again` records the state and the reasons before and after. A delivery whose package file could not be read, or whose check could not run, is checked again only when its folder changes.
- **States.** `incomplete`, `ready`, `needs_attention`, `superseded` (a newer delivery of the same folder arrived before anyone decided, or the pipeline is running again in the folder) and `gone` (the folder or its package file is missing for two rounds while the watch folder was readable; a project folder that cannot be read does not count), each reopened (`import_delivery_reopened`) when the folder is again as it was checked, for example when a lock file of a document that was open on the share disappears again; after a decision `queued`, `imported`, `failed` (until the next round offers it again) or `refused`; `changed_after_import`, the reference delivery of a family whose package folder changed or disappeared after the import, and `archived`, one whose vanished folder a superuser confirmed as deliberately archived (below). A watch folder that cannot be read, or that shows nothing but hidden items while it had open deliveries (a share that is not mounted looks like an empty folder), is skipped that round: nothing is decided. A watch folder that shows anything else, even only folders without a package file, is mounted: the watcher looks into it, so a delivery whose folder was removed is `gone` after two rounds. A watch folder that was emptied completely keeps its open deliveries until a delivery or another folder is in it again.
- **Correcting.** What the pipeline does not know (the clinical status, HPO terms, the inheritance model) or filled in wrongly, a superuser corrects before the approval: `POST /family-imports/deliveries/{id}/revisions` with the revision they saw, a reason and the changes; `GET /family-imports/deliveries/{id}/package` shows the package as the import would read it now, the pipeline's file and every correction. The pipeline's file never changes: every correction is a revision in the append-only table `import_delivery_revisions` (what changed, the value before and after, the reason, who and when, and the whole package afterwards) and an event on the chain `system:import-inbox`. The laboratory's fields change freely, with a reason; sex, parents and couples, which the pipeline used, do too, but as long as a dataset that the pipeline computed with them (`pipeline_used_pedigree`) is in the import, the delivery needs attention (`package_pedigree_changed`). The pipeline's own fields (run, assembly, family ID, sample IDs, files, QC) are refused. A sample that the package's files name but that is not a member, a column of the phased family VCF (`dataset_vcf_sample_unknown`, one reason per column, with the name), is added as a member, with a reason (owner's decision of 2026-11-11): an affected relative for the segregation, or a PGT index that the PED lacks. The sample ID is that of the file; no other member is added to a pipeline's package (`400`). A member that was added in CoGA can be removed again; a member that the package delivered cannot. A member added with parents, or one that is removed, counts as a change to the pedigree the pipeline used. A correction is the list of changes, or the whole package as it was edited (`package`): CoGA then works out field by field what differs, with the same rules. What Discover proposed for a minimal file is already in the package and is corrected the same way. After every correction the delivery is checked again at once, without reading the files again. On the page *Package import*, **Correct…** opens the package as a form (project, analysis, the pregnancy of a NIPT, ROI, PGT details, per member sex, parents, the member it is related to (`related_to`), role, status, carrier status and HPO, the members that are added or removed, and which datasets are in the import), with the reason and the earlier corrections, and shows the package as `coga-package.json`, which *Download coga-package.json* saves. **Package…** shows the package of a delivery that is past correction, with its corrections. **Where in the code:** `backend/app/services/import_delivery_revisions.py`, `frontend/src/pages/dashboard/DeliveryCorrectionDialog.tsx`.
- **Adding by hand.** A folder that no pipeline delivered goes the same way: *Add a folder by hand* under *Deliveries* (or `POST /family-imports/deliveries`) takes a folder under the import folders, the project, the analysis (LR-WGS, LR-AS (long-read adaptive sampling), SR-WGS (short-read WGS), PGT, Expanded Carrier Screening, mNIPT or cNIPT: the package's `analysis_type`), for an mNIPT or cNIPT the pregnancy (*Pregnancy ID*, the package's `pregnancy_id`), and optionally a family ID. If that stays empty, the family ID is the name of the folder; once added, it is fixed, like that of a pipeline. CoGA makes the package that a `coga-package.json` would contain, with the members and datasets that Discover proposes from the folder, and stores it with a delivery of origin `manual` (*Added by hand*). A dataset that the PED's members do not cover (a phased family VCF with a column for a PGT index or an affected relative that the PED lacks) does not stop the proposal: the members come from the PED, the datasets are proposed anyway, and the delivery needs attention (`dataset_vcf_sample_unknown`) until that sample has been added as a member. Such a delivery is checked, corrected and approved like every delivery. Because CoGA made that package, *Correct…* can add any member to it or remove any member from it, and edit the whole package as JSON (*Edit as JSON*); every save is a revision with a reason (owner's decision of 2026-11-11). The family ID, the assembly and the files stay as CoGA read them. CoGA writes nothing into the folder, not even a `coga-package.json`, and computes no checksums (owner's decision of 2026-11-10): the fingerprint guards the folder until the import, and the import records the SHA-256 of every file. Before the import no watcher looks at such a delivery; after the import the watcher follows its folder like that of every delivery (below). Refused: a folder with its own `coga-package.json` (that goes through a watch folder), and a second open delivery of the same folder. **Where in the code:** `backend/app/services/import_manual_delivery.py`, `frontend/src/pages/dashboard/AddDeliveryForm.tsx`.
- **Approving.** Nothing is loaded until a superuser decides, on the page *Package import* (under *Deliveries*) or through the API. `POST /family-imports/deliveries/{id}/approve` (with `dry_run`, `conflict_mode`, `acknowledge_warnings`) approves a delivery that is `ready` (a new family, with `cancel`), or one that needs attention only because its family already exists (`update`, or `overwrite` for an administrator). Warnings must be acknowledged, with their SHA-256 as the list showed them (`warnings_sha256`): if they have changed in the meantime, `409`. The folder must still have the same fingerprint as at the check, and the approval names the revision of the package that the approver saw; otherwise `409`. The import job is queued as the approver, in the project of the package file, with the manifest the delivery keeps, and names the delivery, with the revision and every correction; the family's package record for that analysis keeps them (`delivery`). A real approval makes the delivery `queued`; a dry run leaves it as it is. `POST /family-imports/deliveries/{id}/refuse` refuses an open delivery, with a reason. At the start of every round the watcher records the end of the job: `imported` or `failed`. A failed import is offered again in the same round (the owner's decision, 2026-11-23): if the folder is still as it was checked, the delivery is checked again as a whole, because the failed import may have left the family with the datasets that did succeed (an update then completes them), and it is `ready` or `needs_attention` again, with the failed job named (`import_delivery_offered_again`); if the folder has changed in the meantime, it is `superseded`; if the folder is gone, it is `gone` after two rounds. **Where in the code:** `backend/app/services/import_delivery_review.py`.
- **After the import.** A family has one package record per analysis it was loaded for (`families.metadata.package_imports`, keyed by the key of the package's analysis: its `analysis_type`, for a NIPT with the pregnancy the package names, `monogenic_nipt:ZW1`; the monogenic and the conventional NIPT of each pregnancy each have their own), and everything below holds per record: each analysis's folder is followed against its own reference, never against another's. Every record also lists the storage sources its import wrote, per kind of data (`sources`, from the package's datasets: `package_sources`); the sign-out of that analysis freezes and checks the data under those sources, and the data no other analysis claims (chapter 11, *One sign-out per analysis*). CoGA shows an analysis's reads (IGV), the signal tracks and the QC report from the package folder that its record names (`delivery`). An import with update skips the datasets the family already has; so only an import that read the analysis's data in full, as a new family or with overwrite, says which source files they were. The record keeps that delivery as the reference (`reference_delivery`), with the mode of the import (`import_mode`: `new_family`, `update` or `overwrite`); an update keeps the reference the record had, and an analysis's first package import is its reference, whatever the mode. The rule: the folder from which CoGA shows the source files must be as the reference was imported. That is why, every round, for every record of a family that came from a delivery (including one added by hand), the watcher compares that folder with the reference's fingerprint: only the size and modification time of every file, nothing of the content. A delivery keeps the list over which its fingerprint was taken (`file_listing`, up to 5,000 items). If the fingerprint differs, the reference becomes `changed_after_import`, with what changed (`source_change`: the files added, removed and with a different size or time, each up to 50 paths with the count). Importing the folder's new delivery with update leaves the notice in place: the record then names the new delivery, but the reference stays the previous one, and the folder still differs from it. An update from another folder is also a change: CoGA then shows the source files from that folder. If the folder is unreadable for two rounds while the folder it sits in shows something, that is a change too, with the notice that the source files are not available any more; a folder that cannot be read or shows nothing (a share that is not mounted) decides nothing. A superuser can confirm a vanished folder as deliberately archived (*Confirm archived…*, `POST /family-imports/deliveries/{id}/archive`, with a reason of 1 to 2,000 characters; `409` unless the delivery is `changed_after_import` with a vanished folder): the delivery becomes `archived`, with who, when and why. Sign-out then asks for no reason, but every family page says *Source files archived*, and the record of a later sign-out freezes it; if the folder comes back changed, it is a change again. Every family page shows, for each analysis whose folder changed, a notice *Package folder changed after import* that names the analysis (*The package folder the data of this family's monogenic NIPT of pregnancy ZW1 was imported from …*; `GET /families/{id}`, `package_source_changes`: a list, one item per such analysis, each with the key of its package record in `analysis_type`), the list *Deliveries* shows the reference as *Changed after import*, on the row of the folder's new delivery once there is one (a folder is one row), and sign-out asks for a reason (chapter 11, gate 3b). A notice disappears only when the folder is again as the reference was imported, when a delivery of the same analysis is imported with overwrite, or when the folder's new delivery is refused with a reason; a refused state of the folder is never reported again, a state that was neither imported nor refused is. A delivery that was imported with update while its family still has the notice (a package record names it, with update, and that record's reference is `changed_after_import`) can be approved again by an administrator, only with overwrite (`overwrite_approvable` in the list; 400 for another choice, 409 for every other imported delivery). If that overwrite fails, the delivery stays `imported` (`import_delivery_overwrite_failed`) and the family is back as it was. Every transition is an event on the chain (`import_delivery_changed_after_import`, `import_delivery_archived`, `import_delivery_change_resolved`). **Where in the code:** `backend/app/services/package_changed_after_import.py`.
- **Reporting.** Every transition is an event on the hash-chained audit chain `system:import-inbox`, by `system:import-watcher`. The logs name only counts, never a folder or a family. `GET /family-imports/deliveries` (superuser) gives the deliveries, with their state, reasons and what the package file says.

`FAMILY_IMPORT_ROOTS` is an **allowlist** of the folders that may be scanned. That way whoever imports cannot simply have an arbitrary file on the server read in. A path outside that list is refused: the check reports `package_folder_not_allowed`, and adding a folder outside the list by hand gets `HTTP 403`. If the list is empty, the check is open to any local folder; that is a deliberate development mode. A path that cannot be followed is refused as well (`package_folder_not_allowed`, and `HTTP 400` when adding by hand): a path through a symbolic link that loops, or a path that starts with `~` for a home folder the server does not have.

The list of packages found shows only folders that the check accepts, and reads nothing in the others. So it does not contain: a package folder that is a symbolic link out of the import folders, or a link that loops. A link that stays within the import folders is followed; the folder it leads to is in the list. Typed in, such a folder is refused, with the reason (`package_folder_not_allowed`).

**Where in the code:** `backend/app/services/family_package_source.py` (the allowlist; `_listed_package_folder` checks every folder of the package list as the import does, before the list looks into it).

## What a package contains

A package is a folder with the pipeline's files; the manifest that CoGA keeps for it describes them. The manifest knows sixteen kinds of datasets:

- **Variants:** `snv` (small variants, with an optional annotation table), `sv_needlr` (structural variants), `cnv` (CNV calls with their signal files), `mito` (mitochondrial variants), `repeats_trgt` (repeat expansions).
- **Tracks:** `wisecondorx` and `qdnaseq` (CNV coverage and segments), `ccnv` (the copy number of the maternal plasma in a conventional NIPT, with ccnv's gain and loss calls and its QC), `coverage`, `apcad` and `pcf` (embryo analyses), `haplotypes` (a phased family VCF from GLIMPSE2 or SHAPEIT5).
- **Other:** `paraphase` (paralogous genes), `alignments` (CRAM/BAM for the genome browser), `qc` (sequencing QC) and `pipeline_info` (the pipeline's run record: tool versions and parameters).

The expected folder layout per dataset is in `docs/data-import.md`. The discovery step, with which CoGA proposes what a package file leaves out or a folder added by hand does not have, searches those paths and shows what it found. The long-read pipeline puts the tool version in file names. A search path may therefore contain a `*`, but the manifest always contains the concrete path found, never the pattern.

The discovery step looks for files by the family and sample IDs, and only in the package folder:

- An ID is taken literally. A `*`, `?` or `[` in it matches only itself, so that a sample never gets another sample's file. A leading `~` belongs to the name, not to the home folder.
- An ID is not a path (the ID rule, below). An ID with a `/` or a `\`, or an ID that is `.` or `..`, is refused (`family_id_invalid`, `sample_id_invalid`) before the discovery step looks anything up under it. That way no file named after an ID lies outside the package.
- A PED, a NIPT VCF or a dataset file that is a symbolic link out of the package, or a link that loops, counts as absent, just as the check refuses it.
- A per-sample folder of a long-read package that loops is not a sample, not for the package list either.
- A folder with the name of a PED (`FAM1.ped/`) is not a PED for the discovery step or the package list.

**A folder in the package that is a symbolic link is reported.** The package list and the discovery step read some folders according to the package's layout: `ped/`, a dataset folder of the long-read pipeline (`snv/`, `sv/`, `cnv/`, `repeats/`, `paraphase/`, `mito/`), a folder inside it (a sample's, `snv/HG002/`) and a folder inside that one. If such a folder is a symbolic link, they follow it, wherever it leads: a PED or a per-sample folder behind it puts the package in the list, and the discovery step proposes a member from a linked per-sample folder, even though the content may belong to another family. That is why the discovery step and the check (a dry run, and the import, which runs the check) report every such link as a warning (`package_folder_link`):

- the warning names the folder in the package and where it leads: as a path relative to the import folder that contains it (`COUPLE2/snv/HG003`), or as "a folder outside the import folders";
- a warning never names an absolute path;
- nothing below a link is looked at, and a link that leads to no folder is not reported.

The owner chose a warning, not a refusal (`package_folder_link_issues` in `family_package_source.py`). The guards above still apply: a file that the manifest names or that the discovery step looks for through a link out of the package is still not read.

Every path in the manifest is relative to the package folder (or an absolute path inside it). These get a `400`:

- a path that leaves the package (an absolute path elsewhere, `..` out of the folder, a symbolic link to outside);
- a path that starts with `~`;
- a path through a link that loops.

A leading `~` is not a home folder: CoGA reads none. The check finds a loop by looking up the resolved path, so that Python 3.12 (where `Path.resolve` raises an error on a loop) and 3.13 (where it does not) refuse it alike.

**The package's members are the pedigree.** The import reads no PED: the manifest that CoGA keeps names every member under `family.add_members`, with their sex, parents, role and clinical status. Every member counts as a PED row and goes through the same checks; a member without a role gets one from the pedigree, like a PED row. A manifest that names a PED anyway is refused (`manifest_names_a_ped`); so is a manifest without members (`members_missing`). A PED in the folder serves only the discovery step, which proposes the members from it for a folder that is added by hand. Every per-sample dataset must refer to a member of the family. The manifest may also give carrier status and explicit relationships; a relationship may name only members.

For an import into an *existing* family, CoGA compares the package's members with the family as CoGA knows it: every member, their sex and their parents. A family that holds only the package's analysis, or none yet, takes the package as its pedigree:

- **`update`** adds the members the family lacks, with the relationships the package gives them, and changes no member the family has. The delivery's check warns about it (`package_adds_members`). A package that gives a member of the family a different sex or different parents, or lacks one, needs attention (`package_members_differ_from_family`): approving with `update` is refused (400), and the import itself refuses it too.
- **`overwrite`** makes the package's members the family's pedigree: a missing member is added (or made active again), every member gets the package's sex, role and statuses, a member the package lacks becomes inactive (their stored data stay), and the relationships are those of the package. The family's PED text is the package's.

**A family with another analysis.** A family can hold several analyses, each from a package of its own (the monogenic and the conventional NIPT of one pregnancy, and those of other pregnancies of the same woman; short-read and then long-read WGS of the same DNA), each with its own package record in `families.metadata.package_imports`. An import of the one analysis does not change the other's members behind its back (owner's decision, 2026-11-20). If the family holds a package record of another analysis:

- **Members.** The import keeps every active member of the family, except the members only its own analysis's record lists (`members`): the members of the other packages, and whoever was added or renamed in the members editor. None of them is missing: a cNIPT package with only the plasma updates a family that holds the mNIPT trio. An `overwrite` makes inactive only a member the package lacks that only its own analysis's record listed.
- **Values.** A member the family holds keeps every value it knows: sex, parents, role, clinical status, carrier status with type and evidence, and relationships. The package fills in a value the family does not know, and the delivery's check warns about it (`package_fills_member_values`). It adds the members and relationships the family lacks, but never a second father or mother of a child.
- **Another value.** If the package gives a member of the family a known value that differs from the family's known value, the import refuses, with `update` and with `overwrite`, before anything of the family is written. The message names the member and both values, e.g. *PLASMA1's clinical status is affected in the package, unaffected in CoGA*. The delivery needs attention (`package_member_values_conflict`), and no choice approves it: correct the package (**Correct…**), or the member in the members editor (a new structure version on the audit trail).
- **The PED text.** The family's PED text stays its own: the package names only the members of its own analysis.
- **The region of interest.** The family keeps its region: the package gives one only to a family without one, and an `roi` that is not found clears nothing. If the package's `roi` points to another locus, the import refuses before anything is written (`package_roi_conflict`), and no choice approves it: correct the package's `roi`, or change the region on the family page first.

A package that leaves a value open (phenotype `0` or `-9`, no carrier column, parent `0`) changes nothing of the member: a long-read package without phenotypes leaves the affected proband of the short-read analysis affected.

Both changes happen after the import has marked the family, before the first dataset, through the family-structure service (`family_structure_service.take_package_pedigree`): a new structure version, a pedigree change on the family's clinical audit trail (source: the package import), and the family's analyses marked as outdated. If the family cannot take the change (the structure changed since the import read it, or the sample ID of a new member belongs to another family), the import refuses before the first dataset. If a dataset then fails or the import is undone, the new pedigree stays; the restore puts the datasets back.

**Several pregnancies.** A family can hold several pregnancies of one woman, and each pregnancy's NIPT is an analysis of its own (owner's decision of 2026-11-21). A complete package of a monogenic or conventional NIPT names its pregnancy (`pregnancy_id`: the ID the laboratory gave it, by the rule of a family ID and of at most 64 characters); a package of another analysis names none. The analysis's key is its type with the pregnancy (`monogenic_nipt:ZW1`, `conventional_nipt:ZW1`): a monogenic and a conventional NIPT with the same `pregnancy_id` are one pregnancy.

- **The same or another pregnancy.** A package with a pregnancy the family holds imports that pregnancy's analysis again, like every later import of an analysis (with `update` or `overwrite`); its signed versions stay. A package with another pregnancy is a new analysis beside the others, and changes nothing of their data.
- **Data of its own.** The sources of a pregnancy's calls, coverage tables and ccnv output carry its pregnancy (`suffixed_source`, chapter 3). The father may have the same sample ID in two pregnancies: each pregnancy keeps its own copy of his calls.
- **Plasma and fetus.** A maternal plasma (assay `nipt_cfdna` or `cnipt_cfdna`) and a fetus (role `fetus`) belong to one pregnancy. If a pregnancy's package names a plasma or fetus that the package record of another pregnancy of the family names, the import refuses before anything is written: give that pregnancy's samples IDs of their own, or correct its `pregnancy_id` if it is the same pregnancy.
- **A multiple pregnancy.** A pregnancy whose package names two or more fetuses is a multiple pregnancy; its NIPT results carry a note about it (chapter 8).

**Two samples of one person.** A member of the package can name another sample of the same person with `same_individual_as`: the plasma of a conventional NIPT under another sample ID than the plasma of the monogenic NIPT of the same pregnancy, or the plasma of another pregnancy of the same woman. The manifest gives each pair once under `family.relationships.same_individual`. The pedigree draws the two as one symbol with both IDs, and the Sample QC expects their genotypes to be identical, except for a maternal plasma: that is a mixture of the mother's DNA and a fetus's, and the Sample QC never compares it for identity (chapter 8). Two plasmas of one woman are one person, never one pregnancy: their results stay apart. The other sample may be a member of another analysis's package, but the family must then already hold it as an active member: otherwise the delivery needs attention (`package_same_individual_outside`) and the import refuses before anything is written. Then import the package that names the sample first, or link the two samples later in the family's members editor (chapter 15). A sample is named as its ID is written, case included. The delivery is checked again when the family changes, as at the import of the package that names the sample. A package that makes a new family has its links checked as a structure edit checks them. At every import the samples of one person keep agreeing on their statuses: once the family's pedigree has taken the package's links, the registration reads the family's links, and refuses the import before it writes when the statuses it gives or keeps would give two samples of one person a different known clinical or carrier status. `update` adds the links that name a member it adds; a link between two samples the family already holds without that link, it does not make, and the delivery and the import warn of it (`package_same_individual_not_made`). `overwrite` makes the package's links the family's, also when no member differs, and keeps a link of the family between a member of another analysis and a member of this package, also when the package does not name it itself; the package's link and the family's between the same two samples are one link. If the family holds another analysis, `update` and `overwrite` keep every link of the family between members that stay, also a link between a member of another analysis and a member of this package that the package does not name itself. The field is the laboratory's: a correction of the delivery may change it.

**The PGT pipeline (nf-cmgg/copgtm)** writes its output per tool, with its own PED in `ped/combined.ped`. The discovery step does not read that PED, because it falls short on two points:

- It gives the embryos the sex that ngs-bits inferred from the reads. From that PED, CoGA therefore does not recognise them as embryos.
- It lacks the index: the relative whose haplotypes tell the affected parent's two haplotypes apart.

The family's pedigree is the PED at the top of the folder (`<family>.ped`), which the laboratory puts there; the samplesheet, `dashboard/pedigree.csv` and the pipeline's KING table do not determine it. A folder with only `ped/combined.ped` gives `ped_file_missing`. The PED gives every member in the six standard columns, and what a standard PED cannot say in a column `key=value` after the sixth:

```text
FAM001  FATHER1  0        0        1  -9  role=father   carrier=1
FAM001  MOTHER1  0        0        2  -9  role=mother   carrier=1
FAM001  INDEX1   FATHER1  MOTHER1  1  2   role=proband
FAM001  EMB1     FATHER1  MOTHER1  0  -9  role=embryo
FAM001  EMB2     FATHER1  MOTHER1  0  -9  role=embryo
```

- `role=` gives a member's role (`father`, `mother`, `proband`, `embryo`, `fetus`, `relative`, `sibling`; `fetus` is a pregnancy's fetus in a NIPT, see *The monogenic NIPT* below); without that column the role follows from the pedigree. The sixth column is the clinical status (`2` affected, `1` unaffected, `0` or `-9` unknown), and `carrier=1` (with `carrier_type=obligate` or `proven` if that is known) makes a member a carrier.
- An embryo has sex `0`, unknown before the analysis, and `role=embryo`; CoGA also reads a child of the couple with unknown sex as an embryo without that column.
- The index is every member, outside the couple (the embryos' parents) and the embryos, that is nobody's parent. The couple's child, as above, is the proband.
- Every other index is a relative: through their parents in the PED (the affected mother's sister under the mother's parents, who are then also in the PED), or, if the degree is not known, through the member that a column `related_to=` names. `FAM001 INDEX1 0 0 2 -9 related_to=MOTHER1` makes the index a relative of unknown degree of the mother (`family.relationships.relatives`; several members with commas between them). A standard PED has no column for that; programs that read only the first six columns skip these columns. A member with `related_to=` and without `role=` is a relative in the PED of every family.

The warning `pgt_index` says how the discovery step read each index. An index that is linked in neither way gives `pgt_index_unlinked`: its haplotype stays grey until it is linked, with *Correct…* in *Deliveries* or, after the import, on the family page. For a relationship of unknown degree, CoGA colours the index along the whole genome if it turns out to be a parent or child of that parent (it then shares one of her haplotypes along almost every chromosome). A more distant relative (brother or sister, aunt, cousin) shares a haplotype only over stretches. Those cannot be found marker by marker on imputed low-pass genotypes: they look too much like what unrelated people share by chance. CoGA therefore reads such a relative only at the ROI, as PGT-M reads a distant reference: from the informative markers on both sides. If the 3 Mb on each side show the same haplotype of the parent, CoGA colours that haplotype in the relative over the ROI and those 3 Mb; the rest stays grey, as does a region where a side does not show it clearly.

The parent the pipeline followed becomes the affected parent (`metadata.pgt.affected_parents`), and the index from the PED the index (`metadata.pgt.indexes`). With the inheritance model filled in (`metadata.pgt.inheritance_model`), both get the status the model calls for:

| Model | Parent | Index |
| --- | --- | --- |
| AD, XLD | affected | affected |
| AR | proven carrier | affected |
| XLR | a father affected, a mother proven carrier | a male affected, a female proven carrier |

The validation shows every derived status. A status recorded for the member under `family.members` (or for the added index under `family.add_members`) takes precedence. With AR both parents of an affected child are obligate carriers. If the index is the couple's affected child, the parent the run did not follow also gets the status proven carrier (owner's decision, 2026-10-30); a recorded status takes precedence.

CoGA also reads from the run:

- **PCF:** the segmentation from its table only (`apcad/<embryo>_pcf_mat_data.csv` and `_pcf_pat_data.csv`). A run that draws the PCF only in an HTML plot gets no PCF track.
- **APCAD:** the table of the sites that the run's APCAD read per embryo (`apcad/<embryo>_APCAD_parental_data.csv`: parents homozygous for opposite alleles, the embryo read deeply enough). The embryo's allele fraction comes from `raw_AF` (the column `AF` is the cohort's), the parent from `source`. CoGA reads an embryo without such a table from its trio VCF. Alongside it, the discovery step writes the embryo's segregation table (`apcad/<embryo>_APCAD_segregation_data.csv`, under `segregation:`): the sites where one parent is heterozygous. The `apcad` dataset reads them into the track `apcad_segregation`, for the display of the parental origin of an aneuploid chromosome (chapter 9). The table is checked together with the APCAD files before a track is replaced; a table whose `Indiv` names another embryo fails validation.
- **mtDNA:** the run's mtDNA-Server table (`mito/variants.annotated.txt`, one row per variant per sample, without a chrM VCF). That way every member with rows in it gets their chrM calls. The discovery step links the column `ID` (the sample's chrM BAM) to the member (`table`, `table_id`). The import writes those rows as the member's chrM VCF, with `VariantLevel` as the heteroplasmy level.

**The monogenic NIPT (the NIPT-M pipeline)** delivers one single-sample VCF per parent: the mother's plasma (cfDNA), made with Mutect2 in tumour-only mode, and the father's gDNA, made with GATK HaplotypeCaller. Per sample there is also a table with the coverage per capture target (`coverage_<sample>.txt`). Without a family VCF, the discovery step looks for such a pair: a child from the PED without its own VCF (the fetus), whose mother and father each have a single-sample VCF named after them (`<sample>.vcf.gz` or `<sample>.<anything>.vcf.gz`, in the package folder or one folder deeper). The mother's sample counts as the plasma. The proposal gets:

- `analysis_type: monogenic_nipt`;
- the assay `nipt_cfdna` for the plasma;
- the role `fetus` for the child: the pregnancy's fetus, without data of its own, no proband and no PGT embryo;
- the two VCFs under `datasets.snv.per_sample`;
- the coverage tables under `datasets.coverage.per_sample` as `target_table`;
- the CRAM of the plasma and of the father, with the index beside it, under `datasets.alignments.per_sample`, so the genome browser shows their reads under their calls (`<sample>.cram`, or with the pipeline's tags after a dot or an underscore: `<sample>_<anything>.cram`). When several such files are named after a sample, or the file has no index, none is proposed and a warning says why (`nipt_alignment_not_proposed`);
- a warning (`nipt_pair_detected`) that says which sample was taken as the plasma and which as the father. Whoever imports checks both before the import.

One combined VCF with a column for the father and one for the plasma is also possible, as an ordinary `family_vcf`.

The proposal names no pregnancy: the pipeline's package file gives it (`pregnancy_id`), or *Pregnancy ID* when adding by hand. Without a pregnancy, a NIPT delivery needs attention (`pregnancy_missing`) until **Correct…** fills it in. In a NIPT's package CoGA reads a child of both parents with unknown sex, that is not affected and has no role, as the fetus (`fetus`); a pregnancy can have two or more (a multiple pregnancy).

**A family on classic short-read WGS (Illumina, analysis `short_read_wgs`, SR-WGS)** has at the top of its folder the PED (`<family>.ped`) and the joint GATK callset twice (HaplotypeCaller per sample, genotyped jointly with GenotypeGVCFs): annotated with VEP (`<family>.GRCh38.annotated.vcf.gz`, with index) and unannotated (`<family>.vcf.gz`). Per sample there is a folder with the CRAM (`<sample>/<sample>.cram`, with `.crai`), but it may be missing.

- **Name:** the annotated callset's name may carry a suffix after `annotated` that says what else annotated it (`<family>.GRCh38.annotated.gnomad41j.vcf.gz`); its index is the `.tbi` or `.csi` beside it. A folder with two annotated callsets is refused (`snv_multiple_candidates`): the discovery step chooses neither. Leave one, or name the callset in the package file's `snv` dataset.
- **SNVs:** the discovery step takes the annotated callset as the family's SNV callset; the unannotated one is not read. It sets `source_format: haplotypecaller`, the caller that GATK's header names. That header also describes the physical phasing ("phased"), and the first record can be physically phased (`0|1`); the caller's name decides, so the loader never reads the file as imputed genotypes, which the diagnostic views leave out. A package file that the pipeline writes for such a family had best name the caller in its `snv` dataset too.
- **Records:** GATK without VQSR writes no filter of its own (`.`); the filter *PASS only* keeps such records. The contigs are in the order in which joint calling merged them; the import does not need a sorted order.
- **Annotation:** this annotation names two fields from the VEP cache after their source: `MAX_AF_VEP_ALL_POPULATIONS` (VEP's `MAX_AF`, which the popmax filter reads where gnomAD has no popmax of its own) and `CLIN_SIG_VEP_CACHE` (VEP's `CLIN_SIG`, which stays separate next to the ClinVar file). CoGA reads them under both names.
- **Alignments:** `<sample>/<sample>.cram` is the sample's alignment. A sample without a CRAM has calls, but no reads in the genome browser.

**A couple for carrier screening on the long-read pipeline (nf-core/lrsvar)** has no PED and no joint callset. Each partner has their own files (`snv/<sample>/annotation/<sample>_annot.vcf.gz`, `sv/<sample>/needlr/<sample>_sv_phased.needLR.<version>.vcf.gz`, `repeats/<sample>/<sample>_tr.vcf.gz`, `paraphase/<sample>/<sample>.paraphase.json`). The import page shows such a folder anyway: a folder with the pipeline's per-sample folders counts as a package.

- **Members:** without a PED, the discovery step takes the members from those folders and puts them under `family.add_members`.
- **Sex:** the karyotype with which TRGT genotyped the member's repeats (`--karyotype XX` or `XY` in the `##trgtCommand` of the TRGT VCF). The pipeline takes it from its samplesheet. It is therefore the registered sex, which Sample QC compares with the reads.
- **Couple:** two members of different sex are proposed as a couple (`family.relationships.couples`, context `carrier screening`), the woman as mother and the man as father. The warning `ped_proposed_from_folders` says what was proposed.
- **SNVs:** the two SNV files are read together as one callset, stored under the name of the caller that made them (`snv.per_sample` with `source_format: deepvariant` for the long-read pipeline's DeepVariant files). A site that both partners carry becomes one row with both calls. A partner without a record at the other's variant is read there as reference, as a joint VCF calls a covered site. DeepVariant's `RefCall` and `NoCall` records are kept only where the other partner has a variant.
- **Requirements for the SNV files:** each file contains the sample of its entry (the partner's file is refused) and at least one record (otherwise it is refused before the stored callset is wiped). The files have the same order of `##contig` lines and are sorted in that order. An import that replaces the stored callset brings the file of every sample that has calls in it. A per-sample SNV callset requires `analysis_type: monogenic_nipt` or a `source_format` that names the caller (such as `deepvariant`); otherwise it is an error (see the dry-run, step 6).
- **SVs:** the NeedlR files go under `sv_needlr.per_sample`. A file whose `Query_ID` names another sample, or a file without a record, is refused before anything has been written.

**Where in the code:** `backend/app/services/family_package_discovery.py` (discovery), `family_package_common.py` (the dataset list; `package_path_within` keeps a path named after an ID inside the package folder, `_resolve_package_path` a path from the manifest), `family_package_manifest.py` (reading the PED and the manifest), `family_package_nipt.py` (the NIPT pair), `family_package_long_read.py` (the members of a long-read package without a PED) and `per_sample_small_variants.py` (the per-sample SNV files as one callset).

## The dry-run: checking everything before anything is written

The dry-run is the import's safety gate. It runs the same package checks as a real import, but stops before the first write. Two differences:

- With `cancel`, an existing family or an existing sample is a warning in a dry-run and an error in a real import (`existing_family_or_samples`).
- Whether the package's members fit the existing family with `update` or `overwrite` is tested by the delivery's check; the registration tests it again and applies the change, so only in a real import.

The checks, in order:

1. **Path** — the folder must lie within `FAMILY_IMPORT_ROOTS`, and its path must be one that can be followed: no symbolic link that loops, no `~` for a home folder the server does not have.
2. **Existence** — the folder exists, and the job has the manifest that CoGA keeps.
3. **Manifest version** — `schema_version` must be `1` (if it is missing, a warning follows).
4. **IDs** — the family ID (from the manifest, otherwise the folder name) and every sample ID are printable text without spaces, and not a path. Sample IDs come from `family.add_members`; during discovery also from the name of a per-sample folder of a long-read package, or of a parent that the PED names but does not have as a member. Surrounding whitespace is dropped. An error (`family_id_invalid`, `sample_id_invalid`) is an ID with:
    - a control character (C0, such as a line break, a tab, an escape or a NUL; DEL; or C1, `\x80`–`\x9f`) or whitespace in it;
    - another character that a reader does not see: a character that reverses the writing direction of the text (U+200E, U+200F, U+202A–U+202E, U+2066–U+2069, U+061C), which makes `FAM\u202e100` appear as `FAM001`; a zero-width character (U+200B–U+200D, U+2060, and U+FEFF, also the byte-order mark a text file can begin with); or another character that is not printable;
    - a `/` or a `\`, or an ID that is `.` or `..`. A folder named after the ID, and a path segment of a URL, read such characters as a separator, as the folder itself or as its parent folder. `..` within a longer ID (`F..1`) belongs to one name and stays allowed.

    The message shows the ID with every invisible character as an escape (`\n`, `\u200b`), says what is wrong and where the ID comes from, and names the rule. With such an error the check reads nothing more of the package, and the discovery step proposes no manifest. A request that names an existing family with such an ID gets `400` before the job even exists. The same rule refuses such an ID with a `400` in the Family Builder, on a PED upload and when editing members (chapter 15). The rule leaves capital letters alone, because the storage in production distinguishes them. Only on a file system that does not distinguish them (a bind mount on macOS, during development) do two family IDs that differ only in capitals share every folder named after an ID.

    The same rule holds for the pregnancy of a NIPT (`pregnancy_id`, at most 64 characters; `pregnancy_id_invalid`). A package of a monogenic or conventional NIPT names one (`pregnancy_missing`); a package of another analysis, or without `analysis_type`, names none (`pregnancy_not_nipt`, `pregnancy_without_analysis`).

5. **Members**:
    - every member once, with valid codes for sex and status;
    - every parent is a member, with the right sex;
    - every relationship from the manifest names a member, and a relative of unknown degree (`relatives`) is not linked to themselves, nor to someone who is already their parent, child or partner;
    - the affected parent (`metadata.pgt.affected_parents`) is a parent in the family, and the index (`metadata.pgt.indexes`) another member.
6. **Per dataset**:
    - The files lie in the package and exist. A path outside the package, with a leading `~` or through a loop of links, gets a `400` (see above).
    - A compressed family VCF of `snv`, `sv_needlr` or `repeats_trgt` has an index (`.tbi`, `.csi` or `.idx`). An uncompressed `.vcf` and a per-sample file may go without one. An index that the manifest names must exist.
    - An unknown dataset is an **error**; a missing core dataset (`snv` or `sv_needlr`) gives a **warning**.
    - A per-sample SNV callset (`snv.per_sample`, without `family_vcf`) is allowed only with `analysis_type: monogenic_nipt`, or as a callset of germline calls made one sample at a time (a long-read couple) whose `source_format` names the caller that made them (`deepvariant`, `clair3`…). Otherwise it is an error (`dataset_per_sample_unsupported`), so that a NIPT pair is never read as germline calls. Each of its VCFs contains exactly one sample (`dataset_vcf_not_single_sample`) and needs no index. For a NIPT pair the name of that one column can give a **warning** (`nipt_vcf_column_named_otherwise`, see *The import of a NIPT pair*).
    - A family VCF of `snv` with `source_format: auto` whose header names no caller that CoGA reads (or two different ones), and that contains no imputed genotypes, is an **error** (`dataset_callset_unnamed`): CoGA stores each callset under its caller's name and never guesses it. A `source_format` that is not a callset name (lower-case letters, digits and underscores, starting with a letter) is an error too (`dataset_callset_invalid`).
    - A coverage table (`target_table`) names in its header line the columns `chromosome`, `start`, `end`, `attribute` and `mean` (`coverage_target_table_columns`).
    - Every VCF the import reads (the SNV, NeedlR and TRGT VCF of the family or of a sample, a sample's chrM, chrM SV and CNV VCF, the phased family VCF, an APCAD VCF) is read to its end with the import's own readers, before anything is written. A VCF that cannot be read whole is an **error** that names the file, and for a sample's file the sample too: a `.vcf.gz` cut short or damaged, a BGZF file without its end-of-file block, a text VCF with a name ending in `.gz` (`dataset_vcf_unreadable`); a VCF whose last record is cut short (`dataset_vcf_record_cut`); a VCF larger than the import reads (`dataset_vcf_too_large`). For the calls of a whole genome this read takes a minute or more, once: CoGA remembers per file what the whole read found (`package_file_reads`), and does not read the file again while its size, modification time and change time stay the same, at a correction for example. An embryo's APCAD table and segregation table, compressed or not, are read whole too; a table that cannot be read is an error (`dataset_table_unreadable`).
    - The import refuses some files if they contain no record: a family VCF of `snv`, `sv_needlr`, `repeats_trgt` or `apcad`; a sample's SNV, NeedlR, TRGT or chrM VCF; an embryo's APCAD file; a sample's coverage BED. If such a file has nothing after the header, a **warning** follows (`dataset_file_without_record`), and the import fails that dataset, with the stored data as they were. The check judges a VCF by that whole read; it reads another file up to the first line after the header. A line that the loader cannot read as a record (the `track` line of a BED, a column header) therefore gets through. A HiFiCNV VCF or a chrM SV VCF without a call is a result and gets no warning. For a per-target coverage table, the columns are checked.
7. **Phenotypes (HPO)** — a phenotype table must refer to members of the family; bad rows become warnings.

Every finding has a fixed `code`, so that the UI and an auditor can name an error unambiguously. On a single error the import stops with "Package validation failed; no data were imported." and nothing is written.

**Where in the code:** `backend/app/services/family_package_validation.py`; the rule for IDs in `family_identifiers.py`.

## Data integrity

- **Provenance from the VCF header.** On every VCF import, CoGA reads the `##` lines. From them it derives which caller (e.g. DeepVariant, Sniffles, TRGT, GLIMPSE), which annotation tool (VEP, snpEff, bcftools) and which database versions (gnomAD, ClinVar, dbNSFP, SpliceAI, …) made the data. That is *best effort* and never fails: an unknown header yields less, but does not make the import fail. **Where in the code:** `backend/app/services/vcf_header_provenance.py`.
- **A SHA-256 per source file.** CoGA computes a SHA-256 fingerprint of every source file, in blocks, so that even a CRAM of many gigabytes does not have to fit in memory. An administrator can have that hash checked again later. For very large files (above a fixed size or time limit) the check is skipped and reports `too_large`. A package is hashed where it lies, also on a mounted share or bucket. **Where in the code:** `backend/app/services/raw_import_files_pg.py`.
- **Bounded reading and decompression.** Package files and uploads are read and decompressed within bounds, against "decompression bombs" (chapter 2). Downloads of reference data have their own bound. Uploads, package files and downloads decompress gzip with the same code: every gzip block, not only the first (a bgzip file consists of many blocks), under one limit for all blocks together. A gzip file that breaks off in the middle of a block, or in which something other than a complete block follows the last block, is refused. gzip itself has no end marker, BGZF does: bgzip ends every file with an empty end block of 28 bytes. A BGZF file (as bgzip writes the pipelines' `.vcf.gz`) that does not end on that end block is truncated, perhaps exactly between two blocks. It is refused like a truncated gzip file, always before anything has been replaced: an upload with `HTTP 400`, a package dataset fails (owner's decision, 2026-10-28). The readers that stream a file (the small-variant VCFs, the track files) check the end of the file before they read the first record. A plain gzip file, not written by bgzip, has no end block: if it breaks off exactly between two blocks, that cannot be detected. **Where in the code:** `backend/app/services/upload_safety.py` and `bounded_download.py` (`require_bgzf_file_end`).
- **No escape from the folder.** Every path from the manifest must stay within the package folder (`../../etc/passwd` gives `HTTP 400`). **Where in the code:** `family_package_common.py`.

## What goes into which table

First the import registers the family and the provenance, then the datasets follow one by one. Large numbers of variant rows go to **ClickHouse**; metadata, provenance and per-sample source data go to **Postgres**.

**An existing family in another project.** Registration also links an existing family to the import's project. An import writes only its own datasets, under every project of the family, and an `update` skips the stored ones. That is why, as soon as the import holds its write locks and before the snapshot, every project of the family gets, per callset, a copy of the small and structural variants it does not yet have (`copy_variants_to_linked_projects`, on every import of an existing family). Whoever sees only the new project thus sees all the family's variants, and a failed import that restores the family keeps the copy, as it keeps the link. A callset that the import then rewrites was copied for nothing; that happens only at the first import into a new project. A project on an assembly other than that of the family's stored variants is refused before the family is marked or linked (owner's decisions, 2026-11-10). A PED upload never links an existing family to a project: it refuses the family (`409`) or replaces it, with its variants, by a new one (chapter 3).

**Every track belongs to the caller that wrote it.** A sample can have tracks of one track type from different callers, each under its own source (`source`):

- coverage from a BED (`web`), from WisecondorX, QDNAseq, HiFiCNV and ccnv; segments from the same callers;
- on the APCAD track: that of the dataset `apcad` (`apcad`), HiFiCNV's minor allele fraction (`hificnv`) and a separate BED upload (`web`);
- on `apcad_pcf`: that of the dataset `pcf` (`pcf`) and a BED upload.

The viewers draw each caller's coverage as a track of its own. The mtDNA coverage and the NIPT coverage check without a coverage table read only one track with read depth per sample, never the CNV callers' log2 ratios (chapter 8).

**A coverage BED says what it contains**: read depth or a log2 ratio.

- **Upload:** the form asks *Coverage BED holds* (required, without a default). The API takes it as the query parameter `content=read_depth` or `content=log2_ratio`. A coverage upload without that parameter, or an upload of another track type with it, gets `422` before anything is read.
- **Manifest:** `content: read_depth` or `content: log2_ratio` on the sample's coverage entry. Without `content` the entry is imported as `unknown`, with a warning (`coverage_content_undeclared`); another value is an error (`coverage_content_invalid`).
- **Stored** in the track's registration (`sample_interval_track_sources.metadata.content`), in that of an upload's source file (`raw_import_files.metadata`) and in what the family keeps track of (`imported_scopes`: the BED's scope says per sample what it declared). A later registration of the same BED replaces that; no `overwrite` compares it.

One rule decides what a coverage track contains (`coverage_read_depth.py::coverage_track_content`): for a coverage BED what it declared, for another track what its conversion made of the file (read depth after `none`, a log2 ratio after a log2 conversion, otherwise unknown). The track availability passes it along per caller (`coverage_contents`). A coverage BED without a declaration reads as `unknown`.

An import or upload replaces only the track of its own source: the rows and the registration in `sample_interval_track_sources`. The BED of the dataset `coverage` thus leaves the bins of WisecondorX and QDNAseq (which import before it) and HiFiCNV's depth in place; the APCAD import leaves HiFiCNV's minor allele fraction and an uploaded APCAD in place. An `update` skips a sample only if the track of its own source is there. The BED of the dataset `coverage` and a separate BED upload share the source `web` and replace each other.

A separate BED upload (`POST /bed/upload/{sample_id}/{bed_type}`, for a coverage BED with `content`) first reads and checks the whole file. Without a record of the track type it gets a `400` before anything is replaced. It refuses (`409`) only if rows of a BED of that track type are stored for the sample: the rows, not the registration in Postgres, which a failed restore can leave behind. With `overwrite` it replaces them. Deleting a sample's track type under *Admin → Family & sample data* wipes the tracks of every caller.

**The callset of a separate upload of small variants** is the query parameter `source_format`: a caller's name (`haplotypecaller`, `mutect2`, `clair3`, `deepvariant` or another callset name), `glimpse2`, `mito`, or `auto` (the default), which takes the caller that the VCF header names, otherwise `glimpse2` for imputed genotypes. A file whose caller `auto` cannot tell gets `400`: then choose the *Callset* on the upload page. `nipt`, an imputation other than `glimpse2`, or a value that is not a callset name get `422`.

**A separate upload of small variants** (`POST /families/{family_id}/small-variants/upload`) with `overwrite` first reads and checks the whole file: every record is built as it will be stored (for imputed genotypes also the haplotype blocks), without writing anything. A file that it refuses or cannot read leaves the callset, the haplotype blocks and their registration as they were. It refuses:

- a sample that the family does not have, or no record that it can store: `400`;
- a truncated or damaged gzip file: `400`;
- a line that is too long: `413`.

Only then does it wipe the old data and read and write the file again. So the file streams through twice and is never held in memory as a whole. Without a stored callset it reads the file once.

Values that do not fit (the rule per column is in chapter 3):

- A value that does not fit its ClickHouse column, or is not a number, is stored as missing instead of making the upload fail: a GQ above 65,535 or `inf`, a negative phase set, a QUAL beyond the largest `Float32`.
- A read depth stays as the file gives it, up to 4,294,967,295 reads, so that a mitochondrial or amplicon call keeps its depth.
- A record with a negative POS or a POS beyond 4,294,967,295 has no position. It is skipped and counted among the malformed records (`skipped_malformed`). A file with only such records gets `400`.
- A genotype (`GT`) must be in VCF allele notation (`0/1`, `1|0`, `./.`, haploid `1`). A word such as `HET`, `HOM` or `REF`, or bases such as `A/G`, give `400`; the message names the file, the line and the sample and shows the value briefly. A package dataset fails in the same way (owner's decision, 2026-10-28).

ClickHouse has no transactions. If writing fails after the wipe even so (ClickHouse drops out halfway), the upload answers `500` and the callset is gone: the rows already written are wiped again too. The family then gets the flag `import_incomplete` for what the upload was to bring in (`snv` with its callset, or `haplotypes`), without an import job. Until the callset is uploaded or imported again, the family is on *Import incomplete*: every family page shows that, and the report can be signed out only after an acknowledgement with a reason (chapter 11). What Postgres keeps of the wiped haplotype blocks, and the parents' phase corrections, stay in place until then. Every successful upload removes from the flag what it brought in again, also without `overwrite` (such an upload is refused as long as anything of it is stored). The datasets `snv` and `haplotypes` of a package read their family VCF once with `overwrite`: the import restores an existing family from its backup if a dataset fails.

**A file without a record replaces nothing.** A loader that replaces stored data reads its file before it wipes anything. It refuses a file without a record it can store: only a header, truncated before the first record, or empty.

- **Separate TRGT upload** (`POST /repeat-expansions/upload/{sample_id}`): reads the whole file and builds every call before it wipes the sample's calls or records what it brought in. Without a record for the sample a `400` follows (*No valid TRGT records found*; TRGT writes a record for every locus of its catalogue). The stored calls and what the family keeps track of stay as they were.
- **In a package** the dataset fails without replacing anything for: a TRGT VCF (per sample, or a family VCF without a record for a sample it names); the bins and segments of WisecondorX and QDNAseq; HiFiCNV's copy-number bedGraph and its depth and minor-allele-fraction bigWigs (a depth file without a bin above zero); an APCAD file; a PCF table (both tables of a sample are read before its track is wiped); a Paraphase JSON without a gene; a sample's NeedlR file; a long-read sample's SNV file.
- An APCAD family file replaces only the track of the samples for which it contains values; a sample without a value keeps its track.
- A track file is read up to its first record before the track is wiped. If it breaks off after that, the dataset fails after the wipe, where the reading stops; the family is restored or marked as with every failed dataset.
- **A chrM VCF without a variant record** is a failed analysis (owner's decision). The dataset `mito` checks in each sample's chrM VCF whether it contains a record, before it replaces the calls of a single sample. Without a record the dataset fails and the mitochondrial calls of every sample stay as they were; an import that keeps the family then marks it import-incomplete for `mito`. A separate upload of mitochondrial calls (`source_format=mito`) also refuses such a file (`400`).
- **No call does count as a result** where a sample can have no call:
    - a chrM SV file with its `#CHROM` line and no call (most samples carry no mtDNA deletion) replaces the sample's earlier chrM SVs with nothing;
    - a HiFiCNV VCF without a call leaves the sample without `hificnv` calls, whether or not another sample has one. The dataset `cnv` then ends as `imported`, with its tracks.
- A chrM SV file without a `#CHROM` line is refused before anything of the dataset `mito` has been written.

**Where in the code:** `repeat_expansion_pg.py` (`read_trgt_sample_calls`), `family_package_tracks.py` (`EmptyTrackFileError`).

**First every sample's file, then a single sample's data.** A dataset with a file per sample reads every sample's file (or checks it up to its first record) before it replaces the data of a single sample. A refused file of a later sample then makes the dataset fail without replacing anything. Per dataset:

- `repeats_trgt` reads every sample's TRGT VCF in full, and once more to store them; that way only one sample's calls are in memory at a time.
- `cnv` checks every sample's HiFiCNV VCF (sample column, records) and reads every signal file up to its first value, before it writes a track.
- `wisecondorx` and `qdnaseq` read every sample's bins and segments, and `pcf` every sample's tables, up to the first row, before they wipe a track.
- `ccnv` reads every sample's QC file and calls VCF in full and checks that they give the same result (fetal sex, fetal fraction, sex-chromosome call, sample), and reads the bins and segments up to the first row, before it writes anything.
- `apcad` reads every embryo's file up to that embryo's first value, before it wipes an embryo's track. A VCF in which its reader finds no record is read in full as a BED.
- `coverage` reads every sample's file before it replaces a sample's track: a BED fully decoded (like the BED loader) and read up to its first record, a per-target coverage table fully parsed.
- The per-sample SNV files of a monogenic NIPT are checked for their one sample column and a record before the plasma's calls are written.
- `paraphase` reads every sample's JSON before it replaces a single sample's results.
- `mito` reads every chrM SV file before it replaces a chrM call. A file with only records on other chromosomes is not a chrM callset and makes the dataset fail. An unreadable file makes the dataset fail before the chrM VCFs are written.

An `update` checks no file of a track it leaves in place. A file that passes the check is read again to be stored. If it breaks off after the record where the check stopped, the dataset still fails where the reading stops (see above). A long-read sample's SNV file is checked only up to its first record. A record out of position order therefore shows up only when the callset is written: checking everything first would read the files of the longest import twice.

A TRGT value that is not a number is refused before anything is replaced: a position that is not an integer or is greater than 2³² − 1; a motif count, allele length or purity that is not a number; a purity or methylation `nan` or `inf`. A TRGT upload answers `400` and names the line; in a package the dataset fails. A Paraphase copy number (`total_cn`, `gene_cn`, `highest_total_cn`) that Postgres' `integer` cannot hold (below −2,147,483,648 or above 2,147,483,647, however the JSON writes it) is refused in the same way. The dataset `paraphase` fails, names the sample, the field and the gene, and every sample's results stay as they were. A copy number that is not a number is stored as missing.

**The marker of a separate upload.** A separate upload that replaces stored data wipes those data before it writes the file's rows, and ClickHouse has no transactions. If the process stops in between (a restart, a crash, out of memory), no clean-up runs. That is why the separate uploads of small variants, of structural variants and of an interval track (BED) put a marker on the family before their first write in ClickHouse, like an import:

- an item in `import_unfinished` under a key of its own (`upload-` and an id), without an import job and without an analysis: what an upload brings in belongs to every analysis;
- committed on a database connection of its own, because the upload's transaction holds the family's write locks until it is committed;
- it names per sample, as the upload keeps track of it, what the upload can leave half-written or missing: its callset (`snv` or `haplotypes`); its caller's calls of every sample that the rewrite wipes and writes back (`sv_sniffles`, `sv_spectre` or `sv_manual`), its own sample included; the sample's track (`bed_<type>`).

The marker disappears on commit, and on a failure after which nothing is missing: before the first write, after an SV rewrite that restored the stored rows, or after a small-variant upload without a stored callset that wiped its own rows again. A small-variant upload that has already wiped its callset turns the marker into the flag (above). Otherwise the marker stays and the family is on *Import incomplete* ("A single-file upload … began rewriting this family's data and has not finished"; chapter 11). Every upload or import with `overwrite` removes from it what it brought in again; with the last one the item disappears. An upload without `overwrite` removes nothing from it.

An upload that cannot write its marker writes nothing. The TRGT upload writes only to Postgres, in the transaction that wipes what it replaces, and sets no marker. An import job's claim and its heartbeat read only the jobs (`family_import_jobs`). A marker names no job, so they never take it for a running or stopped import.

**A separate SV upload rewrites its caller's rows of every sample:** it wipes them and writes them back, with the sample's calls changed. If writing fails after the wipe, it writes the wiped rows back and answers `500`, with every sample's calls as they were; if that fails too, its marker stays. Deleting in **Admin** the SVs of a sample, or a sample with its data, rewrites the family's SVs in the same way. A package's chrM SVs (`mito`) are rewritten this way too, and an `update` takes no backup. If the restore then fails, `mito` gets the flag for every sample whose rows held chrM SVs, not only for the samples the dataset names. The same holds for the chrM calls of `mito` and the files of a NIPT pair, which are merged per sample into the stored rows: the flag then covers every sample whose rows held calls. **Where in the code:** `rewrite_family_structural_variants` (`clickhouse_variant_storage.py`), `_rewrite_with_sample_calls` (`variant_upload_service.py`), `FamilyWriteMark`, `mark_family_upload` and `record_family_upload` (`family_package_registration.py`).

**The marker of a deletion.** A deletion of family data that wipes or rewrites rows in ClickHouse also sets a marker before its first write there (`deletion-` and an id). It does so under the family's write locks, and before its own transaction touches the family's row. This concerns: deleting in **Admin** a sample with its data, the SVs of a sample or those of the family; a PED upload or Family Builder that replaces the family; a structure change that wipes the family's data.

The marker names per sample every dataset of the family (`imported_scopes`) that the deletion can leave half-written or missing. A sample that does not belong to the family any more drops out: nothing can bring in its data any more. Deleting a sample with its data thus names every small-variant and SV dataset of the family (which it rewrites) and the sample's tracks. Rewriting the small variants, like rewriting the SVs, puts the wiped rows back if it fails. Deleting a sample's SVs names every SV dataset except the sample's own, whose calls had to go.

- The commit removes the marker (together with the family, when a family is deleted or replaced).
- Deleting a sample also removes that sample's items from every marker, from the flag `import_incomplete` and from the marker of an import that stopped halfway: nothing can be missing from a sample that is gone. A failure or dataset that named only that sample drops out; one that also named other samples keeps those; one of a family file stays, because the others' part may still be missing. No import or upload can bring in a deleted sample's data any more.
- A failed deletion leaves exactly what its writes may have left half-written or missing, given how far it got: what a started wipe may have taken away; what a rewrite that could not put its rows back may have taken away (of every sample); and what a completed rewrite took away (the sample's: its own items, and its part of a dataset in a single family file, such as the direct calls of a family VCF, an item that names the sample).
- A failure before the first write in ClickHouse removes the marker; a process that stops leaves it as it was written. A deletion that cannot write its marker deletes nothing.

If the marker stays, the family is on *Import incomplete* ("A deletion of this family's data … began and has not finished: it is still running, or it stopped or failed part-way"), and the refusal at sign-out names "a deletion of this family's data" that "did not finish" (chapter 11). Deleting in **Admin** one track type of a sample, or a family's small variants, wipes exactly what was asked and touches nothing else: it sets no marker. **Where in the code:** `FamilyDeletion`, `DataReach` and `reached_items` (`family_package_registration.py`), `delete_sample_with_data`, `delete_sample_data_by_type` and `delete_family_with_data` (`admin_service.py`), `_replace_existing_families` (`ped_service.py`), `update_family_structure_for_admin` (`family_structure_service.py`).

**Replacing a family** with a PED upload or the Family Builder (`overwrite`) wipes the family, its small variants, its structural variants and its interval tracks, with the same code as a structure change that wipes a family's data. Their records in Postgres go with the family, and so do its phenotypes: each is recorded as deleted in the clinical audit trail (chapter 11) before the family is wiped. The variants and tracks go last, when the family has been written again, just before the commit. A replacement that is still refused at that point leaves the family with its variants and tracks as it was. It is refused, e.g., for a sample ID of another family, a phenotype that is not `0`, `-9`, `1` or `2`, carriers that the PED does not name, the inheritance model or the ROI, or a database constraint. A header line of six fields, such as `#FID IID PAT MAT SEX PHENOTYPE`, is read as a family and refused for its phenotype. Before its row is touched, the replaced family gets a marker for its small variants, structural variants and tracks (above). If the commit fails or the process stops after the wipe, the family comes back without those data, and marked.

**A per-sample file** is read from that sample's column (`per_sample_vcf_column`). That applies to `repeats_trgt`, `mito` and `cnv` under `per_sample`, the SNV files of a long-read couple, and a separate TRGT upload or a separate Sniffles or Spectre upload of structural variants.

- The column named after the sample (`<sample>_sort`) is read, wherever it is. That way a joint TRGT or Sniffles VCF can be uploaded member by member.
- A single column without a sample name (HiFiCNV's `Sample0`) belongs to the sample.
- If the column names another sample (of this family or another) and no column names this sample, the file is refused before anything of it is written, and the dataset fails (a separate upload gets 400). Likewise a file with two columns for the sample.
- `vcf_sample` on the entry is the explicit word of whoever wrote the manifest: the column it names is read. That way a laboratory that has checked its tubes can link a sample to a file named after another tube.

A separate SV upload also refuses a VCF without exactly one `#CHROM` line before its records. A manual TSV has no sample column: every row is a call of the sample. `mito` and the SNV files check all their files before they write one; with `repeats_trgt` and `cnv` an earlier file of the same dataset may already have been written. A NIPT pair deliberately falls outside this rule: the one column of each file belongs to the sample of its entry.

**An SV record without END or SVTYPE** is read as VCF 4.4 lays it down (`structural_variant_ingest.py`).

- **Without END**, or with END `.`: the record ends at POS + SVLEN (unsigned) for an allele `<DEL>`, `<DUP>`, `<INV>` or `<CNV>`, subtypes included, and at POS + the length of REF − 1 for every other allele (an `<INS>`, a breakend, a sequence allele). That way a deletion with only an SVLEN gets the genes it overlaps: the upload takes the genes that the POS–END range overlaps.
- **Without END and without SVLEN**, one of those four does not say how far it reaches. The record is left out and counted (`skipped_without_extent`), in the upload's answer and in the dataset's summary (owner's decision, 2026-10-27). A file in which every record is like that is refused: an upload with `400`; a HiFiCNV or chrM SV file makes its dataset fail, with the previous calls as they were (a NeedlR file without a call fails anyway).
- **A written END** stays as written, except for a translocation whose INFO/CHR2 names another chromosome: that END is the partner's position, and the record ends at its own breakpoint.
- **Without SVTYPE** (which VCF 4.4 calls redundant next to ALT): the record gets the type its ALT indicates. That is the name of a symbolic allele (`<DUP:TANDEM>` becomes `DUP:TANDEM`); BND for breakend notation (`N]5:3000000]`, or a single breakend such as `G.`); INS or DEL for a sequence longer or shorter than REF; otherwise `SV`.

Those rules also apply to a package's NeedlR, HiFiCNV and chrM files (`record_end`, `extent_not_stated`).

**An SV record without SVLEN**, or with SVLEN `.`, that is written as a sequence allele (REF and ALT are bases of different length) gets the length its alleles give: len(ALT) − len(REF), negative for a deletion (`record_sv_len` in `structural_variant_ingest.py`). VCF 4.4 prescribes SVLEN only for a symbolic allele. With END − POS an insertion written this way (END equal to POS) would count as 0 bp, and a minimum length would drop it. Every SV reader follows that rule: the Sniffles, Spectre and TSV uploads and a package's NeedlR, HiFiCNV and chrM files. A written SVLEN stays as written; END and the SV's id do not change.

**A breakend's partner** (its mate) is between the brackets of its ALT: `N]5:3000000]` has its partner at 5:3000000. Every SV reader (the separate uploads and a package's NeedlR, HiFiCNV and chrM files) reads it with one rule (`breakend_mate` in `structural_variant_ingest.py`, via `parse_bnd_alt`):

- from an ALT in breakend notation, whatever SVTYPE the record has;
- for a translocation (BND or TRA, in any capitalisation) without breakend notation, such as Sniffles 1's `<TRA>`: from INFO/CHR2, if it names another chromosome, and END;
- a single breakend (`G.`) names no partner.

The SV list shows the partner in its columns *Remote chr* and *Remote start*, its CSV export in columns with the same names next to the locus (empty for an SV without a partner). The sentence in the report names it as the remote breakpoint, the Circos plot draws the arc to its chromosome, and the filters *Remote chr* and *Remote start ≥* find the breakend by it. The id of a NeedlR breakend contains its partner, like that of an uploaded breakend (see below).

**The id of a NeedlR SV** consists of its coordinates and type, for a breakend with its partner (`1-7000-12000-DEL---`, `1-20000-20001-BND-5-3000000-3000000`), as a separate SV upload names its call, and never of the record's ID (`_needlr_variant_id` in `family_package_variants.py`). A caller numbers its calls per run (`Sniffles2.DEL.1S0`), so that the files of two samples, or two runs in one family VCF, give the same ID to different calls. The record's ID is kept in the SV's annotation. Reviews, tags and classifications hang on the id.

- One event (same chromosome, start, end, type, partner, REF, ALT and SVLEN) in the files of two samples, or repeated in the family VCF, is one SV with all calls. A sample keeps a genotype over a no-call (`./.`, which a line without `Maternal_GT` or `Paternal_GT` gives a parent), and then its own call (the query call of its line) over the genotype that another sample's line gives it as a parent, whichever file comes first.
- Two calls at one position, type and partner with different alleles, or a symbolic allele (`<INS>`) of a different length, are two SVs: the first keeps the id, the other gets its length as a suffix (`1-20000-20007-INS----7`).
- The same event, uploaded from Sniffles or Spectre, has the same id, and so one review; each caller keeps a row of its own. A record without END also ends, with NeedlR, where the upload makes it end (above), so one call has one id.

Every dataset kind has its own import function in a registry. A kind without an import function is an error: a test guards that, and the import fails loudly on it.

**NIPT artefacts** (the list of recurrent artefacts per assay) are not filled by the package import; they have their own management (chapter 15). The import does add the package's analysis (e.g. `monogenic_nipt:ZW1`) to the family's analyses (`families.metadata.analyses`) and an assay per sample (e.g. `nipt_cfdna`) to that sample's assays, so that the NIPT context is recognised later (chapter 8). The capture panel a package names for a sample (`assay_panel`) is kept per analysis (`assay_panels`): the artefact list reads only the monogenic NIPT's, and a conventional NIPT of the same plasma does not change it. So one family can hold the monogenic and the conventional NIPT of one or more pregnancies, each from a package of its own.

**The import of a NIPT pair** stores the pair as its pregnancy's callset (`nipt_p…`, see *Several pregnancies*). It first reads the plasma's VCF (the sample with the assay `nipt_cfdna`, otherwise the mother), whatever the order in the manifest. Then it merges every other per-sample file with the stored rows (`overwrite_scope="samples"`, as with `mito`): a file replaces only its own sample's calls.

- **Filter on the father:** the father's VCF is largely low-level noise. Of the father's records, the import keeps only a record with a call from 15% alt reads (`NIPT_PATERNAL_KEEP_MIN_VAF`, below the 20% of a heterozygous call, so that no genotype is lost), with a call its caller genotyped as a carrier (a GQ and no TLOD), or at a position where the plasma has a call (an MNV over one of its bases). It counts the others per sample as `skipped_by_filter`.
- **Per-call metrics:** every file contains one sample, so a record's FILTER values and caller metrics (TLOD, FS, mapping quality, …) belong to that one call. They are kept with the call for the quality filter and the de novo triage.
- **Sample column:** the import reads the one sample column of every file as the sample of its manifest line, whatever the column is called. The laboratory links its genetically verified tubes to the files they are in, and a file (and its column) may be named after another tube. If the column is named neither after the sample nor like the line's `vcf_sample`, the discovery step, the dry-run and the import give a warning (`nipt_vcf_column_named_otherwise`) with the sample, the file, the column and another family member the column is named after. The file is not refused (owner's decision, 2026-10-28). A laboratory that has verified the tube puts the column name as `vcf_sample` in the line; the warning then disappears. A `vcf_sample` with the sample's own ID does not do that. The dataset's summary keeps the column read per sample (`vcf_column`).
- In `update` mode the import skips the pair if its pregnancy's callset already has calls.
- A coverage table becomes the sample's track `target_coverage`, in place of the previous one.

The pipeline's **run parameters** (genome build, which caller made which variant class, which steps ran) are in the collapsible section *Analysis pipeline settings* on the family workspace and in the same section of the report, per analysis: a family with short-read and then long-read WGS has a section of each run, with the analysis in its title (`families.metadata.pipeline`, per analysis). In a family of several analyses every section names its analysis, also when only one carried a run record; the report shows only the run record of the analysis it signs out. An import of an analysis replaces that analysis's run record, and a re-import without one leaves none. The **tool versions** appear in the provenance footer and in the line *Modules & versions* of the report.

**Where in the code:** `backend/app/services/family_package_datasets.py` (the import functions per dataset) and `family_package_registration.py` (registering the family, samples and provenance); the display in `frontend/src/pages/families/PipelineSettingsPanel.tsx`.

## Following jobs and handling errors

Every import is a row in `family_import_jobs`, with a status that the database guards: `queued → validating → running → completed | failed`. The row also keeps the validation errors and warnings, the log lines, a summary per dataset and the timestamps.

The requester of a job is the account that requested it (`requested_by_id`). The worker imports as that account, even if its email address has changed in the meantime (which a sign-in with Microsoft can do, chapter 5). A user who is not a superuser or administrator sees no job at all: every route of `/api/family-imports` requires one of the two. A superuser and an administrator see everyone's jobs. `requested_by` is the email address under which the job was requested: the job shows it, but it decides nothing.

The import runs only as long as that account is an active superuser or administrator, as the import routes require. If the account is deactivated, is not a superuser or administrator any more, or is gone when a worker picks up the job, the worker does not run the import. That also applies to a job that was still `validating` and is picked up again after its worker stopped. The job ends `failed` with the reason, nothing of the family is written, and the log names neither the account nor its address. An active superuser or administrator puts the import back in the queue. A job that overwrites an existing family moreover runs only as long as that account is an administrator. If it is superuser or lower by then, the job ends `failed` with the reason (`REQUESTER_CANNOT_OVERWRITE_ERROR`), and nothing of the family is written; an `update`, or an active administrator who puts the overwrite back in the queue, brings the package in. An import that was already running when the account was deactivated or given a lower role runs to the end: the account is checked when the import starts.

A job goes to `running` only once it has recorded the family it imports (`family_id`), before the import writes anything of that family. That is how a sign-out recognises a running import (chapter 11, gate 0b). If that fails, the import stops without writing and the job ends `failed`, with the reason. The job's later updates (log lines, per-dataset summary, heartbeat) are informational: if one fails, the import carries on, because the status and the family stay in place. If an update does not find the job as its worker's any more (another worker ended it), it changes nothing; the backend log mentions that, with the job's id.

**Progress and time left.** Every dataset gets a `progress` in its summary: when it started and ended. Some importers also count how many bytes of their files they have read (for a gzip file the compressed bytes): the small variants (the SNV VCF, the SNV files of a long-read couple, the two files of a NIPT pair and the imputed genotypes) and APCAD. From that follow the part read and the time left: the rest of the files at the pace since the first report. The time before that does not count, because the importer is not reading anything yet then (reading in a VEP table, wiping the rows of an overwrite). An estimate appears only after half a minute of reading. It applies to the dataset that is running; the datasets after it are not estimated, and the page says how many follow.

A worker takes a job atomically (`FOR UPDATE SKIP LOCKED`), so that several workers do not get in each other's way, not even from different processes. A running job writes a sign of life (*heartbeat*) every minute. The database's clock sets the timestamp and judges the age, so that workers on hosts with a different clock agree. If the sign of life is ten minutes old, the process that ran the job counts as stopped (a restart, a crash, out of memory), and the next worker takes over the job:

- If the import had not yet started writing the family (the job was still at `validating`), the worker runs it again from the start. The earlier attempt's log lines stay.
- If it had (`running`), the job ends `failed`, interrupted, and does not run again: a new run does not undo what it already wrote. The log and the per-dataset summary stay as the import left them.

The process may also still be alive and merely have been unable to write its sign of life (no database connection for it, or an event loop kept busy by other work). In that case, too, the import is stopped: as soon as its heartbeat reaches the database again and sees that the job is not its worker's any more, the import stops where it is, as with a stopped process. The error handling below then does not run, and the import writes nothing more. The family keeps the import's item in `import_unfinished`, as the job's *Interrupted* record says, and the write locks on its variants are released with their connection. Until then the import may have run on: an update of the job that does not find a row any more (the progress, or how the import ended) changes nothing, and the backend log mentions it with the job's id. That does not last long. An import whose sign of life has not reached the database for five minutes (half of those ten) stops itself this way, even before a worker can consider the job stopped. The job ends as interrupted as soon as a worker finds its sign of life stale.

**One import per family at a time.** An import holds its family's import lock, on the family ID, from before the registration until it ends, whichever worker or process runs it. The imports of two analyses of one family so run one after the other: the second waits until the first is done, and its log says *Another import of the family is running: this import waits for it to end.* Without that lock one import could register the family (its pedigree, its samples' metadata, its package record) while the other wrote, restored or deleted it.

**The connection of the write locks.** An import holds its import lock and the write locks on the family's variants each on a database connection of its own, and Postgres releases them if that connection drops. That is why a running import checks those connections every ten seconds (`SELECT 1` in the locks' transaction; without an answer after thirty seconds a connection counts as lost). If one is gone, another import or write may already have started. The import then stops where it is and restores nothing: its job ends `failed` with the reason, the backups it made of the family are deleted, and the family keeps the import's item in `import_unfinished` until it has been imported again with `overwrite`.

The error handling is built so that a half-imported family is never left behind unnoticed ("fail-clean"):

- Every dataset is imported separately. If one fails, its Postgres work is rolled back and the import carries on with the rest. What the dataset already wrote to ClickHouse is cleaned up only by the small variants and the haplotypes themselves. Part of another dataset may remain; then what follows below applies (deleting, restoring or the flag `import_incomplete`).
- If the family is **new and nothing succeeded**, the empty family is deleted again, with its ClickHouse rows.
- If an `overwrite` of an **existing** family fails, the family is restored to its state from before the import.
- **Taking turns:** every write on a family's variants (an upload, a deletion, an import) first takes that family's write lock and holds it until the write is committed. An import holds it from before its snapshot until it is done or has restored the family.
    - A separate upload of a sample's TRGT calls or of an interval track (BED) also takes the lock, because the restore also rewrites those rows; likewise an administrator's deletion of a sample's track or TRGT calls.
    - The demo script `scripts/load_demo_quartet.py` loads through the same uploads, and like them keeps track of what it brings in.
    - A track upload with `overwrite` that fails after its wipe also removes the track's Postgres record. A package dataset that replaces a caller's track also wipes that caller's rows for which Postgres has no record.
    - Two writes on the same family therefore run one after the other, even from different workers. The restore cannot undo an upload that came in during the import: that upload waits until the import is done.
    - As long as a family's import job is running or queued, or a writer holds the lock, its report cannot be signed out. A sign-out shares the lock as long as it reads the family (chapter 11, gate 0b).
- In every other case the successful datasets stay and the family gets the flag `import_incomplete`: the failed and the successful datasets, the timestamp and the import job's id. The error per dataset is in that job; the flag does not copy the error text. The partial state is thus visible, not silently "complete": the family is on *Import incomplete* (see *What goes into which table*).
    - **When the flag disappears:** only when an import has imported every failed dataset again, or a separate upload brought it in again, for the same samples and (for the small variants) the same callset (see below). An import that succeeds without that dataset leaves the flag in place and says so in its log.
    - **An `update` is enough:** the failed dataset's rows were rolled back or cleaned up, so the update finds none and imports the dataset in full. A dataset whose rows remained, it skips, and that does not count; nor does a skipped sample. A dataset that it imported for some samples and skipped for others therefore counts only for the imported samples. An `update` reads what is already there from the stored rows (the variants and tracks in ClickHouse, the repeats and the Paraphase results in Postgres), not from what Postgres keeps of a track (`sample_interval_track_sources`). A dataset that it skips for every sample ends as `skipped`, not as `imported`.
    - **What counts as imported again:** a dataset that the import ends `imported`, also with warnings (`warning`: the phenotype rows it refused, it leaves out and names in the job). `registered` also counts, if the package contains nothing for it that CoGA imports (phenotypes without an HPO row, per-sample GLIMPSE2 BCFs, an APCAD BED for the whole family, a pipeline record without versions or parameters): nothing of those can be missing, and that registration completes nothing of data that another import brought in. A dataset that was only registered because the family is not linked to a single assembly, or because a file could not be found or read, does not count: data may be missing there.
    - **Repeated failures:** if a later import fails, the previous import's failed datasets stay in the flag. If the same dataset fails again for another callset or other samples, both stay. The flag keeps per dataset every callset and every set of samples for which it failed, each with the job in which its error is (`failed_scopes`); a dataset leaves the flag only when each of them has been brought in again. `failed_jobs` names per dataset the job of its last failure; the family pages and the sign-out show that job. Each failure also names the analysis of the import it failed in (`analysis_type`: the key of its package record; none for a single-file upload), and `failed_analysis_types` names per dataset the analyses of its failures: a short-read and a long-read package both have an `snv`, a `qc` and `alignments`. The same scope failing in the imports of two analyses is two failures; only an import of the same analysis, or an upload, brings a failure of an analysis in again, and the sign-out of an analysis is held only by its own failures and those of no analysis.
    - **Without a job:** a dataset that failed in a separate upload (or in an import outside a job) has no job there. The family pages and the sign-out then say that no import job keeps track of its error, and never name the job of another failure.
    - **Other shapes:** the flag, the entries in `import_unfinished` and the datasets' scopes each have one shape, and CoGA reads them only in that shape. A value in another shape (e.g. `true`, text or a list) is never read as something it does not say: the read fails (`ImportMarkShapeError`). A sign-out that meets one therefore fails, and the gate stays closed. An import, separate upload or deletion that meets one leaves it as it is; an upload or deletion fails on it.
- **An import that stops halfway**, because its process is gone, carries out none of the above. That is why an import puts a marker on the family before it writes anything of it: an item in `import_unfinished` in the family metadata, with the job, the start, the analysis of its package and the datasets (a new family is created with it straight away). It records there every dataset it finishes, and removes the item when it ends, unless its restore failed halfway (see below). If the item stays, it names a stopped import and the datasets it did not finish: those may be half-written or missing. The family is then on *Import incomplete*. Only an import that succeeds with `overwrite` and imports those datasets again, for the same samples and (for the small variants) the same callset, wipes the item: an overwrite replaces no more than that. An `update` cannot do it, because it skips a dataset for which data already exist, even half-written data. If an import fails after the marker but before its first dataset (e.g. during registration), it wrote none of its datasets: its item then becomes the flag `import_incomplete`, with all its datasets as failed.
- **The backup of a stopped `overwrite`:** an `overwrite` of an existing family first copies its variant and track rows to backup tables in ClickHouse (`<assembly>/SNAPSHOT/<import-job>/…`), to restore the family on an error, and deletes them when it ends.
    - **Process stopped:** the worker that ends the job deletes those tables, and at every start every backup that no running import owns disappears. The family is not restored with it: the Postgres part of the backup was in the stopped process, and the family may have been written to in the meantime.
    - **Backup already gone:** an import that was still alive when its job was ended can reach its restore before its heartbeat stops it, with the backup already gone. That is why a restore first checks that every backup table is there, and wipes nothing if one is missing. The family then keeps what the import left behind and gets the flag `import_incomplete`, with the failed and the successful datasets.
    - **Restore failed:** a restore that fails in another way (e.g. halfway) may have wiped rows of every dataset of the family: table by table, it wipes the family's rows before it restores them from the backup. The flag then names every dataset of the import as failed, also the successful ones and those it only registered, and none as imported. The family stays marked until an import has imported each of them again. The job's record says the same: the table of datasets shows each as failed, with how its loader ended, and the error message names them all.
    - **Postgres after ClickHouse:** Postgres is restored only after ClickHouse, so after such a restore Postgres may still keep track of a track whose rows the restore wiped. An `update` therefore reads the rows: a dataset whose rows the restore wiped, it imports again, and that dataset leaves the flag; a dataset whose rows are still there, it skips, and that dataset stays in the flag.
    - **Data from outside the import:** such a restore also wipes rows of datasets that the import did not bring (e.g. another source of small variants, the SV calls of another package, or data from a separate upload). The flag cannot name those, so the import's item in `import_unfinished` stays as well. As soon as the restore begins, that item names every dataset the family holds in ClickHouse, as its imports and separate uploads keep track of what they brought in (`imported_scopes` in the family metadata), and every dataset of the import, each with its samples and (for the small variants) its callset. A dataset of another import or upload that is only in Postgres (repeats, Paraphase, QC, phenotypes) it does not name: Postgres is restored in one transaction and an error rolls that back entirely, so the restore cannot leave such a dataset half-written.
    - **Recovery:** the family stays *Import incomplete* until each of them has been brought in again with `overwrite`. An administrator does that recovery: an overwrite and a separate upload are reserved for an administrator (chapter 2). So import the whole family again, every package of it, not only the failed datasets, and upload again with `overwrite` what a separate upload brought in. Every import that succeeds with `overwrite`, and every separate upload with `overwrite`, removes from the item what it brought in again; with the last one the item disappears. A dataset of the import that contained nothing CoGA imports also counts by registering it; data that the family holds count only by bringing them in again. An `update` removes nothing from it, because it skips a dataset whose rows are still there; neither does an upload without `overwrite`. The job's log says so and names the datasets, as does the log of every import that still leaves some in place.
    - An import whose process stops during the restore leaves the same item behind. A restore that puts the family back or refuses to begin removes the item.
    - **What a separate upload keeps track of:** what it brought in, in the same transaction as its data. That is recorded under the dataset of the package that brings in the same data (`snv` with its callset, `haplotypes` for imputed genotypes, `repeats_trgt` per sample), or under a name of its own where no package does so (`sv_sniffles`, `sv_spectre` or `sv_manual`, and `bed_<type>`, per sample; `docs/data-import.md`).
- **The small-variant callset:** an import keeps track of the small variants as the callset in which it stores them: in the flag, in its item and in `imported_scopes`. That is the `source_format` that the SNV dataset states. With `auto` (the default) it is the callset that its family VCF contains, read from the file before the import writes anything of the family, as the small-variant loader reads it: the caller that its header names, otherwise `glimpse2` for imputed genotypes (genotype posteriors in the first record, or phased genotypes in a file whose header or name says it is phased). A file whose caller neither the dataset nor the header names is refused. The files of a NIPT pair are `nipt`, those of a long-read couple the callset of the caller that their dataset names.
    - Two imports that both leave `auto` in place therefore complete each other's failed dataset or item only if their files contain the same callset. An import of direct calls does not bring in a family's imputed genotypes again, and vice versa; one caller's calls do not bring in another caller's again. A separate upload and an import bring in each other's callset again if they stored the same one.
    - The import stores the file as that callset. If the file reads as another callset when its dataset's turn comes, it changed while the import was running; it is refused before anything of it is written.
    - A registration whose callset reads `auto` names no callset, and no import or upload completes it, whatever callset that import or upload stores. Such a registration comes from an import that could not read its family VCF when it began (that import then fails on the file, or only registers it). A family that is marked like that stays marked, and its sign-out requires the acknowledgement.

    **Where in the code:** `family_package_datasets.py` (`snv_dataset_callset`, and the SNV importer) and `family_package_registration.py` (`dataset_scopes`, `_scope_covers`).

- On every error the job ends `failed`, never a silent `completed`.
- A failed SNV import cleans up only the rows of the callset it stores, the callset that the flag then names: with `auto` the one from its family VCF (see above). A failed import of imputed genotypes leaves the direct calls in place, and vice versa.
    - An `update` of the SNV dataset also looks at that callset's rows. It skips imputed genotypes if the family already has them, or the haplotype blocks made from them (the loader writes both; the dataset `haplotypes` does the same, and reads the blocks in ClickHouse, not what Postgres keeps of them). Next to direct calls it does import them. Likewise it imports one caller's calls next to another's: a long-read package imported with `update` into a family that holds the short-read callset imports its own callset.
    - If the import could not read the family VCF when it began, it reads it when the dataset's turn comes. If that still fails, it refuses the file as the loader does, before it counts, writes or wipes anything.
    - The clean-up of `snv` and `haplotypes` (for the latter the imputed genotypes and their haplotype blocks) runs only once the loader has started writing in ClickHouse: wiping the callset it replaces, or, without a stored callset, its first insert. A file that the loader refuses earlier, such as a VEP table without a header line, replaces nothing: the family's callset stays, the dataset fails and the flag names it.

**Where in the code:** `backend/app/services/family_package_jobs.py` (the job life cycle, and taking over a job or ending it as interrupted), `family_package_import.py` (the fail-clean rules, and the heartbeat that stops an import whose job was ended), `clickhouse_family_snapshot.py` (the backup of an `overwrite` and the restore) and `family_package_registration.py` (the flag and the marker `import_unfinished`).

## Provenance: the annotation manifest

Besides the hash per file, CoGA keeps an **annotation manifest** per analysis of a family (`family_annotation_manifest`): per tool or database the version, with a detail and, where needed, the version per modality. That way every result can later be traced back to the versions that made it. The rules:

- **Per analysis:** a family sequenced short-read and then long-read, or a family with the NIPT of several pregnancies, keeps a row per analysis (`analysis_type`, the key of its package record). An import writes the row of its own analysis and leaves another's; a single-file upload writes the row of no analysis (`unspecified`), which is every analysis's. An analysis's manifest is its own row over those of no analysis; a sign-out of the analysis freezes that, never another analysis's versions.

- **Refreshed on a new import:** new versions overwrite the old ones per tool; what the new input does not name stays (a new SV import therefore does not wipe the SNV versions).
- **Manual work wins:** an analysis's manifest that was replaced by hand is always recorded as `manual` and is never overwritten by an import. There is no screen for it: only an administrator can replace it, through the API (`PUT /api/families/{family_id}/annotation-manifest`, with the analysis in `analysis_type`). The manifest itself is not an append-only table, but every replacement goes into the clinical audit trail, with the analysis and the manifest before and after (chapter 11).
- **Taking turns:** an import and a replacement of the same family take the same lock before they read the manifest, and an import holds it until it is committed. A replacement therefore cannot fall between an import's read and write; it waits until a running import of that family is done.
- **Together with the data:** the write belongs to the same transaction as the import. The provenance is therefore stored if, and only if, the data it describes are stored as well; an error in the provenance does not break the import.
- **Per modality:** SNV, SV and repeats are annotated by different pipelines and can name different releases of the same database (e.g. two GENCODE versions). That is why the version per modality is stored as well.

**Where in the code:** `backend/app/services/annotation_manifest_service.py`.

## The register of source files

The traceability register par excellence is **`raw_import_files`**: one row per physical source file, with file name, kind, family or sample, storage path, size, SHA-256 and source. A new import of the same file updates the row instead of making a duplicate. Package files are registered in place: CoGA does not move or delete them.

The storage path is read back as given, and a changed database row can name any path. That is why the administration page reads a file only where an import of its family puts it. The real path, with symbolic links followed, must lie in a package folder that a package record of the family names (the `folder_path` of each record in `families.metadata.package_imports`, one per analysis, if that lies under a folder of `FAMILY_IMPORT_ROOTS`, as for the files that IGV reads), or in the upload folder `data/raw_imports`, where every copy of CoGA's own is kept; the file is read through that real path. So the package of another family in the same import folder is not read.

- A row with another path is listed as unavailable, without the path being looked up; downloading and *Verify* give `HTTP 403`.
- The list marks such a row as not read (`outside_read_folders`), and the page says why *Verify* refuses.
- If the family has no usable package folder, or the list is empty (the development mode in which the import accepts any local folder), the page reads only in the upload folder.
- The package folder is that of the family's last import. A file that an earlier import recorded from another folder is shown as not read, just as IGV does not read that folder either.

Whoever deletes a sample or family wipes only CoGA's own copies of uploads in the upload folder. A row that names another path is skipped and logged, and nothing is wiped for it. The copies go only once the deletion is committed: a deletion that fails leaves every file its rows name in place. A copy that cannot be wiped after the commit stays and is logged with its row, its path and the kind of error: a file without a row, never a row without a file. A package folder need not be named after its family, nor an upload folder after the family's current ID.

An auditor can thus trace per family: which files were read in, with which hash or which storage record (to be checked again), in which dataset; with which tool and database versions per analysis (`family_annotation_manifest`); and how the job went, with status, timestamps, log lines and validation findings (`family_import_jobs`). That closes the chain *annotated VCF → stored data → provenance → report*.

**Where in the code:** `backend/app/services/raw_import_files_pg.py` and `family_package_registration.py`.

## The administration page

The page *Package import* (`/package-import`) shows the deliveries and the import jobs.

1. **Deliveries:** every delivery with its state, its problems and warnings. *Add a folder by hand* adds a folder that no pipeline delivered: choose it (or type the path), the project and the analysis. Folders of which every family was loaded completely appear in the list only if you tick *Show imported folders*; a folder whose import was not complete is marked (*import incomplete*, or *import undone* if its last import was undone).
2. **Correcting:** *Correct…* opens the package as a form, with the reason and the earlier corrections. A sample that the package's files name but that is not a member (an affected relative in the phased family VCF) you add under *Add a member*; for a folder that was added by hand, any other member too, and there you also edit the package as JSON. What the discovery step proposed and whoever imports must check (the NIPT pair and a NIPT file whose column is not named after its sample, the couple from a long-read package, the linking of a PGT index) is listed with the delivery's warnings.
3. **Dry run and approval:** *Dry run* checks the delivery as an import would, without writing anything; *Approve…* puts the import in the queue. If the family already exists, you choose a policy for existing data (`update` or `overwrite`); only an administrator overwrites an existing family. If the package's members differ from the family's in more than new members, only `overwrite` is possible.
4. **Following:** under *Recent family imports* are the last 10 jobs; *Show all* shows up to 100 (the maximum of the job history) in a list that scrolls. As long as a job is running, the page refreshes the status and shows per dataset the part of its files read and roughly how long it will still take, at the pace so far (see above). *View* shows the report: counters, errors, warnings, the result per dataset, the log lines, the SHA-256 of the stored manifest and the package's fingerprint.

`docs/data-import.md` describes this way of working with the dry-run first: whoever imports sees the outcome of the checks before anything goes to the database.

**Where in the code:** `frontend/src/pages/dashboard/ImportDeliveriesPanel.tsx`, `AddDeliveryForm.tsx`, `DeliveryCorrectionDialog.tsx` and `ImportJobsPanel.tsx`.
