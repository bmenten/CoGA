# 15. Other modules & administration

This chapter covers the modules that have no chapter of their own: the Clinical CNV Explorer with the knowledge base of clinical CNVs, the gene panels, the exploratory ancestry PCA, the administration functions and their permissions, the in-app documentation, the releases page and the UI telemetry. Guidance for administrators is in the user guide in the app (`frontend/src/content/docs/user-guide/administration.md`); the management of family members and pedigree in `docs/family-member-management.md`; all tables in `docs/database.md`.

## Access as the common thread

Almost every module hangs on one of three gates (chapter 2):

| Dependency | Meaning | Applied to |
| --- | --- | --- |
| `get_current_user` | Every signed-in user with a valid token | The CNV catalogue, reading panels, releases, submitting UI events |
| `get_current_superuser` | A superuser or an administrator: the role `superuser` or `admin` (`has_superuser_rights`) | Creating, changing and deleting panels, the PanelApp import and the Mendeliome; the variant tags, the overview of the preset filters and the sequencing-QC thresholds; the package import (overwriting an existing family only an administrator) |
| `get_current_admin_user` | Administrators only: the role `admin` (`is_admin_user`) | The rest of the administration router `/api/admin`, projects, the account list and the roles, PED and other uploads |

The actor of an action always comes from the token, never from the content of the request.

## Clinical CNV Explorer

The Clinical CNV Explorer (`/cnv-explorer`) lets curators browse the **knowledge base of recurrent CNV syndromes** (e.g. microdeletion syndromes), compiled from sources including ClinGen/ISCA, DECIPHER, OMIM/Orphanet and ClinVar. For each CNV the page shows the data from the knowledge base and the support in ClinVar: the number of (likely) pathogenic ClinVar CNVs (**ClinVar P/LP**) per direction, loss and gain. Each row links to a detail page (`/cnv-details/{id}`), which also links the supporting ClinVar records.

The router `/api/cnvs` has three read endpoints, all behind a login: one CNV by id, the searchable catalogue per assembly, and the CNVs that overlap a genomic range (for the tracks, chapter 9).

**The cytoband.** Each of those endpoints returns a CNV with its cytoband: the one from the knowledge base, or otherwise the bands the region spans in the cytobands of the assembly, the same ones the ideogram draws (`services/cytoband_labels.py`, also used for the small and structural variants). That way a CNV also gets a band if the build could not read the cytobands, or if it was loaded before the cytobands of the assembly. An assembly without cytobands (T2T stores one band per chromosome, with the name of the chromosome) gives no band.

**Rebuilding the knowledge base.** An administrator starts a rebuild from the page *Organisms and assemblies* (`/reference-data`). For a GRCh37 or GRCh38 assembly without clinical CNVs, the backend also starts the build itself: after an import of the assembly from UCSC (as that administrator) and at startup (as `startup-bootstrap`, not an account; `REFERENCE_BOOTSTRAP_CLINICAL_CNVS`). The same applies to the DGV variants: the pinned DGV release (2025-12-01, per assembly by SHA-256 and size, `DGV_PINNED_RELEASES`) is downloaded and committed only if the whole file matches (`dgv_load_jobs`, `REFERENCE_BOOTSTRAP_DGV`; [data-import.md](../../data-import.md#dgv)).

- The heavy build script (`scripts/clinical_cnv_knowledgebase.py`, which among other things fetches ClinVar) runs as a **separate process**. That way the downloads and the extra dependencies do not affect the API process.
- The result goes through the regular reference loader into `clinical_cnvs` and is registered as an import (chapter 13).
- The progress is in `clinical_cnv_kb_jobs`: who requested it, the timestamps, the number of rows and any error.
- The job stores the requester as an account (`requested_by_id`). The rebuild runs, and loads what it built, only as long as that account is an active administrator. This is checked at the start and again just before loading, because the build runs for up to two hours. If the account has meanwhile been deactivated, is not an administrator any more or does not exist any more, the job ends `failed` with the reason, and the previous knowledge base stays in place.
- If the script is missing on the server, the status says so and the backend refuses a rebuild (`503`).

The backbone of the knowledge base is ClinGen's dosage curation and the ClinGen file with the recurrent CNV regions. If the script cannot load either of them, it stops, instead of writing a knowledge base without that source. The rebuild then fails: the error names the source and the reason, the page shows this with the last rebuild of that assembly, and the previous knowledge base stays in place.

The file with the recurrent CNV regions is pinned per assembly to its SHA-256 (`CLINGEN_RECURRENT_CNV_SHA256`). The script reads it only if the SHA-256 matches, and otherwise stops in the same way. For GRCh38 it is ClinGen's file from release V2.1, the same as the bundled file of the segmental duplications. For GRCh37 it is ClinGen's V2.1 file for GRCh37, downloaded from ftp.clinicalgenome.org on 2026-10-27 with the owner's permission.

The script reads the other sources as they are published that day: ClinGen's dosage curation, the UCSC cytobands, ClinVar, Orphanet and a DECIPHER mapping. It records every file it read into the knowledge base, with its SHA-256 and size; a local file (an Orphanet XML or the DECIPHER mapping) under its name, not under its path. The import registers all those files as a release of the knowledge base: the pinned one with release and SHA-256, the others with name and SHA-256. A signed analysis record freezes this. A build that did not register them completely is not loaded.

**ClinVar support.** For each region the build counts the (likely) pathogenic ClinVar CNVs (not the "conflicting" ones) that have enough reciprocal overlap with the region, separately for loss and gain. The direction follows first from the type in ClinVar, then from the copy number in the name of an array record, and only then from words in the name. The counts are written only if ClinVar was actually consulted. A knowledge base without ClinVar is stored as empty in the table and reads in the app as "not recorded", never as 0.

**One rebuild at a time.** The database allows at most one active job: a unique index on a constant (`idx_clinical_cnv_kb_jobs_one_active`) for jobs with status `queued` or `running`. A request during an active rebuild therefore gets `409`, even if two requests arrive at the same time. A running job reports every minute that it is still alive (`worker_id`, `heartbeat_at`). If that signal is missing for ten minutes (e.g. because of a restart or a new deployment of the server), the status request or a new request closes the job as failed ("Interrupted: …"). After that a new rebuild can start. A build that takes longer than `CLINICAL_CNV_KB_BUILD_TIMEOUT_SECONDS` (default two hours) is stopped and marked as failed. That way every job ends as `completed` or `failed`, and no job blocks the next rebuild forever.

**Where in the code:** `backend/app/routers/cnvs.py`; the rebuild in `backend/app/services/clinical_cnv_kb_jobs.py` and the endpoints `/api/admin/clinical-cnv-kb/...`; the pages `frontend/src/pages/cnv-explorer/ClinicalCnvExplorerPage.tsx` and `frontend/src/pages/genome/CnvDetailsPage.tsx`.

## Gene panels

A **gene panel** is a named list of genes (optionally with regions and repeat loci) that delimits variant filters. The catalogue feeds the panel filter on the filter pages (chapter 8) and in the Variant Explorer, which applies a panel as the family page does (chapter 14), and the panel membership in the Gene Explorer (chapter 13).

- **Reading** (every signed-in user): the list, one panel, its versions, and searching in PanelApp.
- **Writing** (only a superuser or administrator, `get_current_superuser`): creating, changing, deleting, importing a PanelApp panel and rebuilding the Mendeliome. Checking gene names for an edit (`POST /api/panels/genes/check`) is also for them: it only reads, but it is a POST, like the edit it serves.

**Versions.** A panel gets version 1 when it is created, built (the Mendeliome) or first imported from PanelApp. It gets a next version each time its genes or regions change: through an edit (for a local panel also a new description), a newly built Mendeliome with different genes, or a new PanelApp import with different genes or regions. Each version is stored with the full gene and region list, the source, the external version and who made the change (also as text, so that the person stays recognisable if the account disappears). That way it can be traced which gene set a panel had at a given moment. The app never rewrites a stored version, and the database refuses a second version with the same number. No trigger, however, makes the table `gene_panel_versions` append-only. **Note:** deleting a panel also erases its version history. That is why *Delete* in the list first asks for a confirmation, which names the panel and its version; only that confirmation sends `DELETE /api/panels/{panel_id}`. *Cancel* and Escape send nothing.

**HGNC symbol or Ensembl gene ID.** A panel names each gene by its HGNC symbol or by its Ensembl gene ID (`ENSG` and eleven digits; a version such as `.24` is dropped, in upper case or not). The ID is the stable name of the gene: a symbol can be renamed or read as another gene. CoGA looks up a gene with an ID through that ID, in every reference that gives its genes an Ensembl ID (the GENCODE one), and the gene gets the symbol that this reference gives it (that of the first loaded assembly: GRCh38, then T2T, then GRCh37). In a reference without Ensembl IDs (the RefSeq reference of T2T), CoGA looks up that symbol, and only among the genes without an ID: another gene with the same symbol and an ID of its own is never the panel's gene. The panel filter keeps the variants of such a gene through the ID and the symbol in their annotation (the annotation of an SV names genes only by their symbol) and through its positions. The symbol is stored with the gene in `gene_panel_genes.symbol` and in every stored version (`gene_panel_versions.gene_symbols`); a reference that later gives the ID a different symbol turns the same list into a new version at the next edit. The page shows such a gene after its symbol, e.g. *BRCA1 (ENSG00000012048)*. A symbol that names the gene of one of the panel's IDs is that gene: the panel keeps it once, under its ID. A gene from PanelApp gets the Ensembl ID that PanelApp gives for it (with PanelApp's symbol if no loaded assembly knows the ID); the Mendeliome names its genes by their symbol.

**Unknown names.** A gene name that no loaded assembly knows (a typo, an old symbol, a withdrawn Ensembl ID) stays in the panel's gene list but gets no region: a filter on the panel finds no variant in it. The panel's page lists such names as *not imported* (the genes without a region in any assembly).

**Editing a local panel.** On the panel's page a superuser or administrator removes a gene with the bin icon on its row, adds names, or edits the whole list. All three produce the same list of changes (*Changes for version N*). Nothing is saved until the confirmation. The names to add are checked beforehand (`POST /api/panels/genes/check`); a name that no assembly knows is flagged, and an Ensembl ID appears with the symbol of its gene. The confirmation sends the full new gene list with the version the change was made on (`expected_version`). The backend reads the panel `FOR UPDATE` and refuses with `409` if the panel has a newer version by then: otherwise the list would silently undo the changes of that version. The page then reloads the panel and keeps the changes ready to be confirmed again.

**PanelApp.** A superuser or administrator searches and imports panels from Genomics England PanelApp.

- **Searching.** Each panel found shows its number of genes, regions and repeats, and how many of them PanelApp rates green, amber and red. CoGA reads those numbers from PanelApp for the version found (`GET /api/panels/panelapp/{panelapp_id}/counts`). Entities without a rating (level 0, including what an expert review removed) are listed separately as *unrated* and are never imported.
- **Three imports per panel:** *Green*, *Green + amber* and *Green + amber + red*, each with the number of genes it takes in. Each choice is a separate panel in the catalogue, with its own name (e.g. “PanelApp 285: Intellectual disability (green + amber)”), versions and genes, to filter on separately (`external_selection`: the levels, lowest first). The row shows which choices are already in the catalogue, with their version. In addition, the user chooses the assembly, and whether regions and repeats are included.
- **What is stored.** The PanelApp id, the version, the source URL and the chosen levels. The PanelApp version (`external_version`) is separate from the panel's version in CoGA.
- **Importing again** (from another release or with other options) gives the panel of that choice a new version if its genes or regions change. If they stay the same, the panel keeps its version and no new version is archived; the import does record the PanelApp version, the choices and the time. The panels of the other choices stay as they are.

The key of the ranking cache (chapter 12) contains the version of the panel and its genes and regions. A ranking on the earlier genes is therefore not an exact hit, nor does it serve another panel.

**Mendeliome.** A generated panel with the genes that have a causal or associated relationship with a disorder in the Monarch knowledge graph. It is rebuilt when a new Monarch release is loaded, and then gets a new version if its genes change (chapter 12).

The UI hides the write buttons from anyone who is not a superuser or administrator, but the protection is on the server.

**Where in the code:** `backend/app/routers/panels.py`, `backend/app/services/panel_metadata_service.py`, `panelapp_service.py` and `ensembl_gene_ids.py` (the form of an Ensembl gene ID); the pages in `frontend/src/pages/panels/`.

## Ancestry PCA (exploratory)

**Outside the intended purpose.** The section *Ancestry (exploratory)*, the last card of a family's Sample QC (`FamilyAncestryPanel.tsx` in `FamilySampleQcPage.tsx`), shows how genetically similar each member is to public reference populations. It is not validated and not for clinical interpretation, and never enters a sign-out or a signed record (TF-01 §4, TF-15 §3). The section and its plot say so: *Exploratory — not for clinical use*. It projects each member onto four fixed principal components of a public reference and plots it next to the reference individuals. The explanation for developers is in `docs/ancestry-pca.md`.

**What a projection reads.** The family's stored small variants in ClickHouse, at the reference markers only (`ancestry_callsets.read_marker_rows`): the callsets `clair3` (direct calls), `nipt` (the per-sample calls of a NIPT family) and `glimpse2` (imputed genotypes). That takes less than a second; no VCF is read again and nothing is registered.

**What a callset covers: measured, not declared.** A sequenced genome carries the ALT allele at about two in five markers (Hardy-Weinberg from the reference frequency). The coverage of a callset is the number of markers with a non-reference call for the member, divided by that expectation, inside and outside the exome mask:

- **a call at every marker** (`complete`): an explicit genotype call at at least 95% of the markers; a missing record does not count;
- **genome**: at least 75% inside and outside the exome; a missing record is homozygous reference;
- **exome**: at least 75% inside the exome, less outside it; a missing record is reference inside the exome mask, outside it the marker is dropped;
- **part of the markers** (`partial`: a gene panel, part of the sites, a filtered imputation): less than 75% even inside the exome; not projected.

Of the callsets a member can be projected from, CoGA takes the direct calls first, then the per-sample NIPT calls, then the imputed genotypes. A cfDNA sample from maternal plasma and an embryo are left out; the other members of such a family are projected.

**A choice per member.** Whoever may change the project can make a different choice from CoGA's for one member (`ancestry_choices`, `PUT /api/families/{family_id}/ancestry/choices/{sample_id}`): read one callset (this is also how you include an embryo), with the regions that callset covers (from a gene panel: the coding markers of its genes; or from a BED file of a capture kit, via `…/bed`), leave the member out, or go back to *Automatic*. With regions, the callset is read within those regions (`regions`) if it carries at least 75% of the expected non-reference calls there; a missing record counts as reference there. Of a BED file, CoGA stores only the markers in it, the number of intervals, the name and the SHA-256, never the file. A cfDNA sample gets no choice. Choices are append-only (`ancestry_sample_choices`); the latest one for a member applies. Saving queues a calculation, and each result stores the choice it read.

**The calculation.** Per member and marker, the dosage is the number of ALT alleles of a diploid call with exactly the REF and ALT of the marker that passes its filter; a call without a filter (`FILTER=.`) counts for imputed genotypes and for a callset that filtered no call at all. Any other call, or two rows of one callset at one position, leaves the marker out. The PCs are the least-squares fit of the reference axes to the usable markers, so that a marker left out does not pull the point towards the centre. A member is projected with at least 1,000 usable markers (`MIN_MARKERS`) and 95% of the covered markers usable (`MIN_CALL_RATE`); otherwise the table says why not. Each coordinate gets a standard error: the spread of the fits over 200 resamplings of the usable markers (`pcs_se`); the plot draws a dotted ellipse of two standard errors around each point.

**When it runs.** The ancestry worker runs where the package import runs: in the import worker processes, or in the API if the API runs import workers itself (chapter 4). Every 30 seconds it queues an automatic job (`ancestry_runs`, `trigger = 'automatic'`) for each family on GRCh38 whose last import has completed and none is running, if no job has yet read the data version of its small variants or if a choice is newer than the last job. *Calculate PCA projection* queues one by hand (`trigger = 'user'`). No import or upload calls it. A completed job writes one append-only snapshot (`ancestry_results`): the four PCs of each member or why not, the callset it was read from and how, the scan of each callset, the data version read, the calculation version and the rules. A failed or interrupted job publishes nothing.

**The reference.** `backend/app/data/ancestry/1000g-grch38-v1.npz`: 2,504 individuals from the 1000 Genomes Project (phase 3, five superpopulations) and 9,569 autosomal GRCh38 SNPs, derived from the pinned public files of peddy, which chose its SNPs in exome capture regions. The exome mask (`1000g-grch38-v1.exome.json`) marks the 8,398 markers in the CDS of a protein-coding transcript of GENCODE v50, or within 20 bp of it. The four PCs come from the reference alone, so that family data never determine the axes. The SHA-256 of the model and of the mask are pinned (`DEFAULT_REFERENCE_SHA256`, `DEFAULT_EXOME_MASK_SHA256`); `ANCESTRY_REFERENCE_PATH` selects a custom model, which is checked against its own JSON file. Each projection keeps the reference it was calculated with (`ancestry_reference_panels`), and stays readable on its own axes.

**The locks.** A calculation checks the family under the write locks on its variants, closes that transaction and reads the markers. It takes the locks again to write its result, and refuses if the family's variants were written to in the meantime or its members changed. That way an import or a sign-out never waits for the PCA.

**Access.** A reader of the project sees the section; calculating by hand and choosing require the right to change the project. A family or project outside the user's projects answers `404`, like an unknown one. The tables are in chapter 3.

**Where in the code:** `backend/app/routers/ancestry.py`; `backend/app/services/ancestry_service.py`, `ancestry_callsets.py`, `ancestry_choices.py` and `ancestry_projection.py`; the section `frontend/src/pages/families/FamilyAncestryPanel.tsx` with `AncestryChoices.tsx`.

## Administration functions

The whole administration API is in `backend/app/routers/admin.py` (`/api/admin`); every endpoint requires `get_current_admin_user`, except the variant tags, the overview of the preset filters and the sequencing-QC thresholds, which require `get_current_superuser`. The screens are in `frontend/src/pages/admin/`, with `AdminDashboardPage.tsx` as the entry point. A superuser sees only their five workspaces there: *Gene panels*, *Sequencing QC thresholds*, *Package import*, *Variant tags* and *Preset filters* (`visibleAdminGroups`); the others are for an administrator (chapter 2).

### Users and projects

- **Users:** per user the e-mail address, name, affiliation, sign-in method, date added, status, role, active and project access, with the accounts awaiting approval at the top. An administrator activates or deactivates an account, sets its role, one of the five (`PATCH /api/auth/users/{user_id}`, chapter 2), archives or restores it, and deletes an account that was never active (`DELETE /api/auth/users/{user_id}`, chapter 5), each time after a confirmation; project access is only shown there. The page says to whom the mail about a pending account goes and sends a test mail. If an administrator makes an inactive account active, the user receives a mail (chapter 5).
- **Projects of a family:** which projects see a family. The data inventory (`GET /api/admin/data`) shows them per family; `PUT /api/admin/families/{family_id}/projects` changes them. The small and structural variants of the family move along (`family_project_variants.py`): each project that is added first gets a copy of the family's rows, and as soon as the new links are committed, the rows under the projects the family left disappear (chapter 3). A project on a different assembly from the family's variants is refused (`409`).
- **Deleting a project** (`ProjectsPage.tsx`, `DELETE /api/projects/{project_id}`): a project to which families are linked is not deleted. The server refuses with `409` and states the number of families (`delete_project_record`, the owner's decision of 2026-11-10). The reason: together with the project, the database would erase its links (`ON DELETE CASCADE`), but the small and structural variants of a family are stored in ClickHouse per project and would be left behind under the deleted project. A family without another project would then have no assembly and show no variants; a family with other projects would keep a copy that no reader looks at. Each family therefore first moves to other projects, or to none, or is deleted, under *Admin → Family & sample data*; its variants move along (chapter 3). The page disables *Delete project* as long as the project has families and says why, with the number (from the project list, which an administrator sees in full). A project without families first asks for a confirmation that says what goes with it: the access it gave its members, and its review tags (which stay on their reviews, marked as deleted). Only the confirmation sends the request. *Cancel* and Escape send nothing.

### Data management and provenance

- **Data management** (`DataManagementPage.tsx`): per family the members, samples, project access, assay data and raw source files, with for each kind of data the number of rows in Postgres and ClickHouse. Every deletion requires `confirm=true`: per kind of data of a sample or family, or a whole sample or whole family. An interval track that more than one caller of a sample filled (the coverage of a long-read sample from HiFiCNV, WisecondorX and QDNAseq, or the segments) is also deleted per caller. The inventory counts each caller separately (`track_source_counts`). `DELETE /admin/data/samples/{sample_id}/{tracktype}?source=…` deletes the track of that one caller (rows and record) and leaves the others in place. Deleting a sample or family is also entered in the clinical audit trail of the family: a sample as a pedigree change, a family as the last line of its trail (`family_deleted`, chapter 11).
- **Source files** (`RawFileProvenanceTable.tsx`): all raw source files of a family, with storage path, size and SHA-256. A file can be downloaded (`410` if it is missing from its path) and **verified**: the backend recomputes the SHA-256 and compares it with the stored value (chapter 6).
- **Pedigree export:** a PED file per family.
- **Family structure:** editing members, parent-child relationships, partners, relatives of unknown degree and the affected and carrier status. See `docs/family-member-management.md`.

    - **One editor:** the members table *Family members* on the family page (`FamilyMembersCard.tsx`), the same one as in *Admin → Family & sample data*. *Edit members* turns each row into its fields, with a row to add a member. The dialog of a member edits the same draft (`familyMembersDraft.ts`), with the sample ID and the HPO terms in addition. Only an administrator edits the members; an analyst changes only the HPO terms in the dialog.
    - **One save.** *Save changes* sends everything in one `PUT /api/families/{family_id}/structure`: each member under its saved ID, with `new_sample_id` if it is renamed, the removed members, and the relationships only if one of them changed. The editor never sends `carrier_evidence`, so that the derivation of a carrier status from the import stays in place.
    - **Checks.** A check refuses inconsistent pedigrees, and the backend shows beforehand what a change affects. Removing a member happens at the save, after a confirmation that shows what it affects, and makes the member inactive. Renaming a member is refused as long as genomic data are attached to the old sample ID.
    - **The ID rule.** A sample ID that an edit gives to a member (a new name, a father or mother, a member that the structure adds) follows the same rule as at import: printable text without spaces, and not a path. Surrounding whitespace is dropped. An ID that the rule refuses is refused (400) before anything is read or written under it: with a control character (such as a line break, a tab, an escape or a NUL) or whitespace in it; with a character that reverses the writing direction or has no width; with a `/` or a `\`; or an ID that is `.` or `..` (chapter 6). A batch or structure change with such an ID renames nobody.
    - **The data.** The imported data are kept; whatever depends on the changed details is marked as outdated in `families.metadata.derived_data_status`. Only `clear_existing_genomic_data` erases the data (the interface never sends it). The marking then says that the data were not kept, and the version row in `family_structure_versions` counts what was erased. The variants and tracks in ClickHouse go last, just before the commit, after every other write of the change. That way a change that fails earlier puts the family back with its variants and tracks.
    - **Traceable.** Each change to the pedigree becomes a new structure version (append-only and hash-chained per family) and a `pedigree` line in the clinical audit trail, with who made it and each changed member before and after (chapter 11).

### ClickHouse maintenance

Per assembly: the status of the tables, and maintenance actions behind a confirmation: creating or updating tables, merging parts (*optimize*), rebuilding the gene index of the small variants, and an integrity check (chapter 11). Without a check being started, the page also shows the last result of the scheduled integrity check per assembly and when it ran, or that it could not run (`GET /api/admin/clickhouse/variants/integrity-monitor`, administrators only).

### Family statuses

The catalogue of work statuses (e.g. "Solved", "Analysis in progress"). Deleting a status does not delete a family: its status field becomes empty. The status and the assignment of a family itself are set by whoever may change the family: an analyst of one of its projects with the role `analyst` or higher, a superuser or an administrator. Whoever is newly assigned a family receives a mail (chapter 2).

### Sequencing-QC thresholds

On the page *Sequencing QC thresholds* a superuser or administrator sets a **warning** and a **fail threshold** for each QC metric, per profile:

- **One profile per assay.** One threshold cannot serve two assays: what is normal for a long-read genome is a failure for a panel. A family uses the profile from its metadata, and otherwise the default profile (there is exactly one).
- **The metrics are in the code, the thresholds in the database.** Which metrics exist, and whether a low or a high value is the failing side, follows from what the QC parsers write; whoever sets the thresholds cannot reverse the direction. A threshold on a metric that has dropped out of the catalogue assesses nothing. The page shows such thresholds below the catalogue, with *Remove*, through the same confirmation and reason as every change.
- **No default thresholds.** A threshold is a clinical decision; none are shipped. Without a threshold, a metric is reported as *not assessed*, never as passed.
- **The bounds of the cNIPT rule.** The profile *Conventional NIPT* holds the bounds of a conventional NIPT's automatic result (`cnipt.*`, chapter 8). The rule reads them there itself and compares as each bound's help text says. As long as QA has not set a bound, it applies a provisional value from the code and the result marks it as provisional.
- **One verdict for everyone.** The backend evaluates the thresholds, so that the workspace, the sample QC and the report show the same verdict. The mtDNA thresholds also come from here.
- **The verdict in the members table.** The chip *Seq. QC* on the family page shows, per sample, the worst verdict next to the mean depth. A sample that passes shows only the number (without a number: *Pass*). Every other verdict is shown as a word: *Warning* (orange), *Fail* (red), or *Not run* (grey) for a sample that was not assessed, because no threshold is set for any of its metrics or the server returned no verdict. That way a sample that was not assessed never reads as passed, not even without colour. If a sample has no mean depth or N50, the chip shows the verdict with the value of the metric that determined it (*Fail ADO 14.2%*): the first metric, in catalogue order, with the verdict of the sample. That is the case for an embryo that is only in the family tables of the PGT pipeline; its QC is then only its `pgt` part (allele drop-out and drop-in and the Mendelian concordance before and after imputation, in %). If no metric determined the verdict (*Not run*), only the verdict is shown. A `-` means that there is no sequencing QC to show for the sample. The tooltip appears on mouse hover and on keyboard focus, also on a chip without a QC report. It names each metric over its threshold, with its value rounded as on the chip and the threshold as set, in the unit of the metric (*Mean depth 18.6x below 20x*), or says why the sample was not assessed.
- **Strictly recorded.** A change requires a confirmation that repeats both values, and a **reason**. It goes into the append-only table `qc_threshold_changes`, with the value it replaces and the reason. A trigger refuses updates and deletions, and the runtime role `coga_app` has no privileges for them (chapter 2). The HTTP audit log does not know the previous value: only here can you see who lowered a threshold and from which value.
- **All values on the Sample QC page and in the report.** Next to the integrity checks, the per-sample table on the Sample QC page shows every sequencing-QC value under the column group *Sequencing & embryo QC*: one column per metric, and in the column *Seq. QC* the worst verdict. These are the mean depth, the alignment metrics from Qualimap, and, for an embryo from the PGT pipeline, the allele drop-out and drop-in (Picard) and the Mendelian concordance before and after imputation (RTG Tools). The latter are the numbers from the pipeline's dashboard; the import reads them from the pipeline's tables (`picard/<family>_ADO_ADI.csv`, `rtgtools/<family>_{cohort,imputed}_concordance.csv`). A value over its threshold is shown with its verdict; a value without a threshold is shown, not assessed. They are not sample integrity checks: they do not change the ring and the status of the sample or the overall verdict of the page, and they do not hold back the sign-out. The signed version shows every frozen value per sample, not only those over their threshold.

**Where in the code:** `backend/app/services/qc_threshold_service.py`; the page `AdminQcThresholdsPage.tsx`; the chip `frontend/src/pages/families/SampleQcCell.tsx`; the columns on the Sample QC page `sequencingQcColumns.tsx`.

### The repeat catalogue: cut-offs and count correction

- **Per locus the cut-offs and a register** (`AdminRepeatLociPage.tsx`, *Repeat catalogue* under *Reference data*). At the top is the STRchive release the cut-offs come from (*Cut-offs from STRchive v2.28.0*, with a link to that release); they are not validated per locus (the owner's decision, 2026-11-16). Each row of the repeat catalogue shows the cut-offs (*normal 6–26 · grey zone ≥ 27 · pathogenic ≥ 36*), the disease with a link to the locus page on STRchive, QA's count correction (*TRGT’s count −1*; *None* if there is none), with the reason, who and when, and how many stored calls name the row. The rows that the laboratory's TRGT catalogue refers to come first. What is known about TRGT's count at a gene (*FMR1*, *HTT*, *POLG*) is shown alongside.
- **The count correction.** *Set count correction* opens the dialog with the field *Count correction*: a whole number from −20 to 20, the number of repeats that CoGA adds to TRGT's count before classifying it (0 for none). The field shows the current correction. For *FMR1*, a note next to the field says that a fixed correction is wrong there (TRGT counts 1 to 3 too low, depending on the AGG interruptions): leave it at 0. Nothing is pre-filled.
- **Always with a reason.** A change requires a confirmation and a reason (e.g. the report, the checked TRGT catalogue and version). It is an event in the clinical audit trail, on the chain `system:repeat-loci`, with the correction before and after; the history is at the bottom of the page. A correction applies immediately. At each locus, the repeat page and the genome tracks mark (corrected) counts close to a threshold (chapter 8).

### The NIPT artefact list

- **Per assembly and assay** (`AdminNiptArtifactsPage.tsx`, *NIPT artefact list* under *Variant configuration*, for an administrator only). At the top you choose the assembly and the assay scope: `nipt_cfdna`, or the capture panel that a cfDNA sample names in `assay_panel` (`GET /api/admin/nipt/artifacts/scopes`). Each scope says how many cfDNA samples it has, across all projects, and how many alleles it lists. The table shows for each allele its source (`curated` or `auto`), its recurrence, its label and when it was added and updated, with a filter on variant or label. Every analysis of the assay leaves the listed alleles out (chapter 8).
- **Automatically, with a preview** (`GET /api/admin/nipt/artifacts/auto-seed/preview`, `POST /api/admin/nipt/artifacts/auto-seed`): the variants that recur in several cfDNA samples of the same assay, across all projects, as an unexplained call with a low allele fraction: below 0.25, and the father of that family does not carry the allele (*Minimum samples*, `min_unexplained_samples`, three by default). That number becomes the recurrence of the allele on the list. A maternal het or the paternal allele of the fetus does not count, however often it recurs: those are the sites the fetal fraction relies on. *Preview* shows, without writing anything, which alleles the seed would add, and which are on the list already: of those it only refreshes the recurrence, their source and label stay. *Seed the list* asks for a confirmation; the seed then reads the samples again and shows what it wrote. A pregnancy without a sample of the father cannot explain a paternal allele; in a large cohort of such pregnancies a polymorphism can therefore still end up on the list. Review the automatic entries. A seed is one clinical audit event, `nipt_artifacts_auto_seeded`, with the threshold and each added variant with its recurrence.
- **From the pipeline** (`POST /api/admin/nipt/artifacts/import`): the list of recurrent artefacts of the NIPT-M pipeline (`recurrent_cfdna_artifact_filter_*.tsv`), after a confirmation. The page then shows how many rows it read, how many the table does not flag or are unreadable, how many alleles it added and how many it refused as frequent or for ClinVar. An import is one clinical audit event, `nipt_artifacts_imported`.
- **One allele by hand** (`POST /api/admin/nipt/artifacts`, *Add an entry*): as `curated`, with a label, after a confirmation. The page reads a typed allele (`7-1000-A-G` or `chr7:1000:A:G`) into the form in which the list stores it. If it is on the list already, the dialog says so, and the allele keeps its recurrence. *Remove* takes an entry off after a confirmation, without a reason: the audit event `nipt_artifact_removed` keeps the entry as it was.

The seed and the import take in no frequent variants, and no variants with a ClinVar classification of pathogenic, likely pathogenic or conflicting. An allele that no family carries yet, or that is added by hand, is not checked when it is listed. That is why every family analysis checks the listed alleles again against its own annotation, and keeps a frequent or ClinVar-pathogenic allele, marked `artifact_list_protected`. Every change is in the clinical audit trail, on the chain `system:nipt-artifacts` (chapter 11); a preview writes nothing.

## UI telemetry

Besides the HTTP audit log, CoGA records **meaningful interactions** in the interface that the backend does not otherwise see: clicks on buttons, links and tabs, and navigation within the app.

- **In the browser**, `frontend/src/lib/telemetry.ts` captures those events. It sends them every five seconds in small batches to `POST /api/ui-events`, and, when the page is hidden or left, with a `keepalive` request. Telemetry never disrupts the app. A batch stays in the queue until the API accepts it. If it does not arrive because of a network or server error, it is sent along again the next time; if the page closes while it is on its way, it goes with the `keepalive` request.
- **The token.** The request on leaving cannot wait for a new token and sends the session's token. That is why the timer refreshes the session's Microsoft token as early as five minutes before it expires, even if there is nothing to send, and again when the page is hidden or shown again.
- **Waiting in the browser.** If the token has expired anyway (the device was asleep, or MSAL needs the user), if the API refuses a batch because the session is not valid any more (`401`), or if a `401` on another request ended the session, the browser does not send the events only to have them refused, nor does it throw them away. They wait in the browser's `localStorage`, under the account under which they were created (the object ID of the Microsoft token), at most 200 per account. They go along with the first request of that account that gets through again (after a refreshed token or a new sign-in), never under another account. The events of the `keepalive` request also wait in this way, even before it leaves. They disappear from the browser only when the API accepts them (a 2xx response). If the request fails, the API refuses it, or the page closes before the response arrives, they go along with the next request of that account that gets through.
- **Multiple tabs.** Each stored event is under its own key. That way two tabs that write at the same time do not overwrite each other's events. At worst both tabs send the same event; the server stores it once.
- **Without a session** (on the login page, or after the session ended), an event is not recorded. The server records each event of a batch as an action of the user of the token that sends it, and no account made such an event.
- **On the server**, `ingest_ui_events` filters. Only a fixed list of types is accepted (`click`, `navigation`, `submit`, `view`, `query`). In paths, ids are masked and query strings are reduced to their keys, so that clinical identifiers are not stored. Sensitive fields (password, token, …) are masked, nested structures reduced to their type. The actor comes from the token. Each event carries the id that the browser gave it (`event_id`, a UUID). The server stores it under that id, and the INSERT does nothing for an id that the table already holds. That way a batch that the browser sends again ends up in it once. An event without a UUID from the browser gets one from the server.
- **The timestamp** `occurred_at` is the clock of the browser. The server accepts it only if it lies between one day before and five minutes after receipt (without a time zone, UTC applies). Otherwise it stores the time of receipt, and puts the client's value in `detail._client_occurred_at`, a key that the client cannot set itself. That way even a timestamp before the year 1 in UTC (`0001-01-01T00:00:00+05:00`) does not make the write fail.
- **Storage:** the events go to the table `ui_events`, through the same lossless queue as the HTTP audit log (chapter 7). An event that the database does not accept is logged with its content and counted. The batch still gets 202, so that the browser does not send again anything that is already stored.

**Where in the code:** `frontend/src/lib/telemetry.ts`, `backend/app/routers/ui_events.py` and `backend/app/services/ui_event_pg.py`.
